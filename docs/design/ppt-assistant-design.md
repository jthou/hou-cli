# PPT 助手设计

**时间**：2026-03-28；**修订**：2026-03-29（两大功能；百炼 + Python PPT；UI §2.1；**后端 §6.5 模块化 + CLI 同步测试**）  
**范围**：在 Hou CLI 上交付 **两条主能力**：（1）长文 → **`ppt_elements`**；（2）元素 → **`slide_deck`（PPT 页面级稿）**。  
**拟定推理与多模态**：**阿里云百炼（DashScope）**——**文本模型**负责抽取、分页、长文合并轮；**多模态模型**负责带图/截图类输入的理解（与文本链路可串接）。调用方式与现有 **`LLMService`**、**`BAILIAN_API_KEY` / `DASHSCOPE_API_KEY`**、`BAILIAN_BASE_URL`（compatible-mode）等保持一致；具体 `model` / `vl model` 由配置与元数据指定，本文不锁死模型 ID。  
**拟定文件侧**：**Python 生态下与 PPT/.pptx 相关的工具均可纳入选型**（§0.5.2），以 **`python-pptx`** 为 **读写 .pptx 的主路径**；其它库按场景叠加（商业库、COM、无头导出等）。产出可以是 **JSON/Markdown** 与/或 **由 `slide_deck` 生成的 `.pptx`**。  
**当前不接** MediaWiki、不接 `pdf_to_wiki` 流水线；**`pptx_*` 异步任务与专用 `builtin`** 仍 **暂不强制**（见文首范围、§9），但与「用 Python 在服务内写 `.pptx`」**不矛盾**。**.ppt（二进制）** 不列为默认支持格式。**后端**须 **模块化** 且具备 **同步 CLI 测试**，与 UI 共用同一套业务步骤（§6.5）。

**仓库现状**：尚无 PPT 专用实现；本文为设计；合入后更新文首三分表。

## 0. 适用范围（部署假设）

- 默认 **内网 / 自用工具**；不展开对外合规全表。
- **技术依赖概览**：推理侧 **阿里云百炼**（见 §0.5.1）；文件侧 **Python PPT / `.pptx` 工具**（见 §0.5.2）。长文 **分块与拼接** 在应用层实现，与是否导出 `.pptx` **解耦**。
- **权限模型**：仅对话/粘贴时无用户磁盘路径；若服务端写 `.pptx` 或读用户 deck，须对齐现有文件类任务的 **路径校验** 与 **日志不上屏全文**（可比照 `pdf-to-wiki-vision-extract-design.md` §2.4）。

### 0.5 可用工具栈：百炼 + Python PPT

#### 0.5.1 阿里云百炼（DashScope）

| 用途 | 模型类型 | 说明 |
|------|----------|------|
| 功能一：长文 → `ppt_elements` | **文本** | 分块抽取、全局合并轮；可配置 `BAILIAN_MODEL` 或与 `LLMService` 一致的 model 覆盖。 |
| 功能二：`ppt_elements` → `slide_deck` | **文本** | 分页、过渡页、讲者备注生成。 |
| 输入含 **插图、扫描段落、幻灯片/页面截图** | **多模态（VL）** | 理解与转述为可并入 `ppt_elements` 的要点或 `layout_hints`；与纯文本链路 **串接或并行再合并**。 |

- **不在本文锁死**：具体 `model_id` / `vl_model_id`；若需与工作助手、图生等能力 **计费隔离**，可用单独 env 前缀或 metadata 覆盖（实现时补全）。

#### 0.5.2 Python 生态：PPT / `.pptx` 相关工具（可全量纳入选型）

以下 **均可作为实现手段**；按 **许可证、部署环境、精度** 选用，在 `pyproject.toml` / 运维文档中登记。

| 层级 | 代表库 / 手段 | 典型用途 |
|------|----------------|----------|
| **核心** | **`python-pptx`**（MIT） | 创建/打开 `.pptx`，写标题、正文、项目符号、**讲者备注**，按母版/layout 加页；`slide_deck` → 文件的主实现路径。 |
| **渲染 / 导出位图** | **LibreOffice** `soffice --headless`、**unoconv** 等子进程 | `.pptx` → PDF/PNG，供多模态输入或缩略图；依赖机器安装，CI 可 skip。 |

**原则**：凡 **成熟、许可证可接受** 的 **Python** 侧 PPT/演示文稿工具（含商业与平台专用），**均允许** 进入本功能的技术方案；**优先** 用 `python-pptx` 保持可维护性与 MIT 友好，再按需累加。

## 1. 两大核心功能

### 1.1 功能一：从长文章中提取 PPT 表达元素

**目的**：把 **叙述型长文** 压成 **适合做幻灯片材料的语义原子**，而不是直接逐段复制正文。

**输入**：**长文章**（纯文本 / Markdown），或 **文本 + 附图/截图**（走 **百炼多模态**，见 §0.5.1）；可选 **元信息**：体裁、受众、时长或 **页数上限**（软约束）。

**输出**：中间结构 **`ppt_elements`**（见 §3），典型包含但不限于：

- **一言概括**、**听众应带走的一句话**（elevator takeaway）。
- **层级提纲**：章节 / 小节与 **可独立成页的候选标题**。
- **论点与要点**：每条论点下 **短句要点**（适合上屏 bullet，非长段落）。
- **证据与引用**：可单独成页或附在要点下的 **短摘录**（控制字数）。
- **数字与对比**：值得放大的 **数据、比例、前后对比**。
- **术语表**：需定义或脚注的 **专有名词**（可选）。
- **版式提示**（弱）：如「时间线」「二分对比」「列表型」，**不**承诺渲染。

**质量要点**：**去水**、**一条一点**、**禁止**把整段原文堆进单条要点；对超长输入需 **分块提取再合并**（§4）。

### 1.2 功能二：生成 PPT 页面（**默认一张幻灯片**）

**目的**：把 **`ppt_elements`** 变成 **`slide_deck`**。**默认产品心智**：用户粘贴一段长文或一节教材，要在 **同一张幻灯片** 上展示 **关键元素**（4～10 条短 bullet + 标题），而不是自动拆成很多页演讲稿。

**输入**：**`ppt_elements`**；**`single_slide`**（默认 `true`）：为 `true` 时 `slides` **仅含 1 页**；为 `false` 时允许多页、过渡页等与旧版一致。可选 **生成约束**（风格、备注等）。

**输出**：**`slide_deck`**（见 §3）。单页模式下若模型仍返回多页，**后处理**合并为一张（要点去重、上限约 14 条）。

**与功能一的关系**：功能一仍可做结构化抽取，但提示词偏向 **单屏可承载** 的要点密度；功能二在默认模式下回答「**这一张怎么摆**」。多页为 **显式可选**（API / CLI `--multi-slide` / 前端勾选）。

## 2. 端到端数据流

```
长文章 (+ 可选元信息)
        │
        ▼
┌───────────────────────┐
│ 功能一：提取元素       │  ← 长文策略：分块 / 分层摘要（§4）
│ 输出：ppt_elements    │
└───────────┬───────────┘
            │ 用户可编辑
            ▼
┌───────────────────────┐
│ 功能二：生成页面       │
│ 输出：slide_deck      │  → JSON / Markdown；可选 `python-pptx` 等 **写成 `.pptx`**
└───────────────────────┘
```

**短文捷径**：字数低于某阈值时，可实现为 **单次调用**：长文 → 直接 `slide_deck`，内部仍建议 **逻辑上** 区分「提取」与「分页」两段 prompt，便于迭代与单测。

**`.pptx` 导出**：**允许** 在任一迭代将 `slide_deck` **映射为** 模板 `.pptx`（§0.5.2，主用 `python-pptx`）。**读入** 已有 `.pptx`、**整页截图 + 百炼多模态** 逆向 enrich `ppt_elements` 为 **扩展能力**（§8）。

### 2.1 界面布局（参考写作助手）

**参照**：写作助手页 `frontend/react-app/src/pages/ArticleWriting.jsx`——**左侧会话列表、中间对话、右侧文章预览**；右侧预览与公众号草稿一致，使用 **`MarkdownPreview`** 等组件，强调 **「一边产出、一边可读的预览」**。

**PPT 助手主工作区**（可与写作助手 **同应用、不同路由**）：在 **不削弱「输入 vs 结果」对比** 的前提下，采用 **两栏**：

| 区域 | 内容 |
|------|------|
| **左侧：输入** | **长文**：大文本区（Markdown/纯文本），可粘贴全文；可选 **附图 / 截图**（多模态上传）；**参数**：受众、页数或时长软约束、是否先只跑「提取」等。**操作**：「提取 PPT 元素」「生成页面」（或一步「提取并生成」）。若有会话/历史需求，可 **仿写作助手** 保留窄条 **会话列表** 或 **顶栏切换会话**，避免占满第三整列。 |
| **右侧：输出 + 预览** | **子 Tab**：**ppt_elements**（JSON）、**slide_deck**（JSON）、**预览**（默认图文并茂对照）。**预览 Tab 纵向分两区**（上下结构）：**上：文本内容**——`slide_deck` 转成的 **Markdown 稿**（只读展示，便于核对标题/要点/备注字面）；**下：PPT 预览**——同一段 Markdown 经 **`MarkdownPreview`** 渲染，对齐写作助手预览样式，模拟「幻灯片可读版式」（当前仍以文字层级为主，插图为后续 §8）。窄屏时预览区上下顺序不变。另可选 **下载 .pptx**（后续）。 |

**窄屏 / 移动端**：整页 **纵向堆叠**（左输入 → 右栏）；右栏内 **预览 Tab** 仍为 **上文本、下渲染**，两区各自可滚动。

**前端固化（与智能助手一致）**：PPT 助手页使用 **`localStorage`** 键 `hou_cli_ppt_assistant_draft_v1` 持久化 **输入框、右侧 JSON/Markdown/预览 Tab、多页开关** 等；**刷新或重新进入路由不丢失**（同源本机）。提供 **「清除草稿」** 清空本地项与表单（不经过后端）。

**与写作助手差异**：写作助手以 **线性长文** 为主预览；PPT 助手预览以 **分页卡片** 为主（必要时段内可嵌 Markdown 片段）。样式（间距、字体层级、暗色主题）宜与写作助手 **同一 Design token**，减少割裂感。

#### 前端实现原则：优先组合，控制冗余

- **总原则**：**优先用已有组件与钩子组合出新页**，不为 PPT 助手 **平行重写** 一套与写作/工作助手等价的会话、预览、模型选择逻辑；新增代码以 **胶水层**（布局、路由、`slide_deck` ↔ Markdown 的薄转换）为主。
- **禁止**：大段 **复制粘贴** `ArticleWriting.jsx` 类页面成为第二份维护副本；若与写作助手共享「左中右」或「侧栏+主区」范式，应 **抽取共用布局或 hooks**（一次抽取、两处引用），或 **单页多模式**（需产品同意时再定）。
- **建议复用（仓库现状-oriented，实现时以实际导出为准）**：

| 能力 | 优先复用 |
|------|-----------|
| Markdown 渲染 / 预览 | `MarkdownPreview`（与写作助手、公众号预览一致） |
| 编辑区 + 预览 + 操作条 | 视交互复杂度参考 `MarkdownEditorPreview`、`MarkdownActionButtons`（复制等） |
| 模型选择 | `useSelectableModels`（`context` 可扩展或沿用 `article_writing` 模式再议） |
| 会话 / 参考块 / 持久化 | 与 `articleWritingIndexedDB`、工作助手会话模式 **对齐字段与隔离策略**，避免第三套 IndexedDB 协议 |
| 表单参数、按钮组 | 已有 `TaskParamsForm`、通用 Button/Input/Collapse 等 **Design system** 组件 |
| 分页卡片预览 | **薄封装**：map `slide_deck.slides` → 卡片列表（标题+`ul`），备注用 Collapse；**不** 新建重型幻灯片编辑器 |

- **新增量预期**：仅限 **PPT 专属** 的输入参数、`ppt_elements` 树/表单编辑、`slide_deck`⇄Markdown 字符串转换、以及可选 **下载 .pptx** API 对接；其余 **尽量零重复**。

## 3. 数据契约（建议 schema）

实现时可加 `version` 字段；以下为 **首版推荐**。

### 3.1 `ppt_elements`（功能一输出）

```json
{
  "version": 1,
  "meta": {
    "source_hint": "可选：标题或来源一句",
    "audience": "可选",
    "constraints_note": "例如页数上限、时长，由调用方写入"
  },
  "one_liner": "全书/全文一句话",
  "takeaway": "听众应记住的一句",
  "outline_sections": [
    {
      "id": "sec-1",
      "title": "第一节标题",
      "summary": "本节一句话摘要",
      "key_claims": [
        {
          "claim": "论点短句",
          "bullets": ["支撑要点1", "支撑要点2"],
          "evidence_quotes": ["可选：短引文≤40字"]
        }
      ]
    }
  ],
  "highlight_numbers": [
    { "label": "例如增长率", "value": "32%", "context": "可选一句" }
  ],
  "terms": [{ "term": "术语", "definition": "一句定义" }],
  "layout_hints": [{ "section_id": "sec-1", "hint": "对比 / 时间线 / 列表" }]
}
```

字段可按产品删减；**核心**是：**可调度的语义块**（论点 + 短要点 + 可选证据），而不是幻灯片逐页稿。

### 3.2 `slide_deck`（功能二输出）

**默认（`single_slide=true`）**：`slides` **只有一项**，`index` 为 1。下例为 **单页**；多页模式仍可用同 schema 扩展多张。

```json
{
  "version": 1,
  "deck_title": "演示总标题",
  "slides": [
    {
      "index": 1,
      "kind": "content",
      "title": "页标题",
      "bullets": ["要点一", "要点二", "要点三"],
      "speaker_notes": "口播提示"
    }
  ]
}
```

多页示例（`single_slide=false` 时）：可含 `transition`、`title` 等。

- **`kind`**：可选枚举 `content` | `transition` | `title`（封面），便于前端或日后模板映射。
- **落地**：用户侧可见 **JSON** 或 **等价的 Markdown**（如每页一节 `## 第 n 页` + 列表）。

## 4. 长文章策略（功能一）

| 问题 | 建议 |
|------|------|
| 超过上下文上限 | **分块**（按标题 / 固定字符窗口 + 小幅 overlap）；每块调用「局部 → 局部元素」；再 **合并轮** 归并 `outline_sections`、去重论点。 |
| 层次太深 | 合并轮显式产出 **扁平提纲** + **key_claims**，避免只堆层级标题。 |
| 成本与延迟 | 合并轮可缩短输出；对超大输入 **限制** `outline_sections` 数量或 `key_claims` 条数（metadata / env）。 |
| 与功能二衔接 | 合并后的 `ppt_elements` **完整** 传给功能二；若超长，功能二亦可 **只接收摘要版**（产品决策：可在 `meta` 标明 `reduced_for_deck: true`）。 |

**失败与降级**：某块提取失败 → 该块占位说明 + 继续其余块；合并轮失败 → 降级为「仅输出大纲 Markdown」。

## 5. 非目标（首版）

- **Wiki / MediaWiki**、与 `pdf_to_wiki` 混编。
- **不默认**：`pptx_*` **异步任务**、专用 **`builtin`**（与 §0.5 **用 Python 直接写 `.pptx`** 不冲突）。
- **默认不承诺**：完美支持 **`.ppt`（二进制）**；**WYSIWYG** 网页拖拽编辑器另立项。
- **不** 自动生成可编辑 **矢量** 图表；**不** 承诺与任意**复杂母版**像素级一致（有限模板 + `python-pptx` 为主）。

## 6. 安全与日志

- 首版数据在 **对话/请求体** 内：遵循现有 Chat **不落全量敏感日志** 的惯例；长文 **DEBUG** 可截断。

### 6.5 后端：公共逻辑模块化 + 同步 CLI 测试（与 UI 步骤一致）

**目标**：避免「UI 一条实现、测试另一套脚本、路由里再抄一遍」；**同一套业务步骤** 供 HTTP、CLI、单元测试引用。

| 要求 | 说明 |
|------|------|
| **公共模块** | 功能一（长文 → `ppt_elements`）、功能二（`ppt_elements` → `slide_deck`）、长文分块/合并、（可选）`slide_deck` 与 Markdown 互转、（可选）写 `.pptx`，须落在 **独立 Python 包/模块**（例如 `backend/services/ppt_assistant/`，具体路径实现时定），以 **无 FastAPI Request 依赖** 的纯函数或服务类方法为主；**禁止** 把完整流水线只写在 **route handler** 或前端独占的私有脚本里。 |
| **HTTP 薄层** | Web API **仅** 负责：鉴权、解析请求体、调用上述模块、序列化响应、错误码；**不** 内联与 CLI 无关的第二条业务分支。 |
| **CLI 同步测试** | 提供 **同步** 子命令（遵循仓库既有 **Typer / Click / argparse** 惯例），典型形态：读 **stdin 或 `--input` 文件** → 调 **与 API 相同的入口函数** → 将 `ppt_elements` / `slide_deck` 以 **JSON 打印到 stdout** 或 `--out` 路径。用于 **CI 与本地回归**，无需启动浏览器或异步 Playwright；与 **UI 在用户点击后触发的后端步骤序** **一致**（同一函数调用链，仅 I/O 不同）。 |
| **测试分层** | **模块单测**：契约校验、分块边界、mock `LLMService` 的拼接顺序；**CLI 集成测试**（仍同步）：起进程或 `CliRunner`，fixture 文本进、JSON 出，断言 **步骤** 与契约，**不做**全文 golden；可选 `@pytest.mark.integration` + 真实 Key 夜间/手动。 |

**不一致即视为缺陷**：若 UI 能走完而 CLI 无法复现，或 CLI 走了私有代码路径，应 **收敛到公共模块**。
