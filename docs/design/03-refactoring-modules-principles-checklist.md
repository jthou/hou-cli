# 公共模块与一致性：原则与清单

**时间**：2026-03-28  
**用途**：指导后端/前端抽取 common、utils、domain 能力与组件重组；减少重复、统一 UI 与 CLI/HTTP 行为，便于测试与组合式重构。  
**地位**：规范取向的清单文档；具体目录命名可与 `00-architecture-design.md` 对齐迭代。

---

## 1. 目标

- **可读性**：改一条业务线时，入口目录清晰，不必在 api、utils、handlers 之间反复横跳。
- **可测性**：规则与转换放在纯函数或小模块里，单测覆盖，少绑 FastAPI/React。
- **一致性**：同一规则（校验、枚举、提示词、页码解析等）**单点维护**；Web 与 CLI 消费同一契约。
- **可组合**：大块逻辑拆成可命名步骤，便于换实现、加特性或并行演进。

---

## 2. 原则

### 2.1 分层与归属

1. **API 薄、领域厚**  
   HTTP 路由负责：参数绑定、鉴权、状态码与序列化。业务步骤放在 **domain / services**，不在路由里堆流程。

2. **`utils` 不设垃圾桶**  
   与具体业务语义强相关（PDF、Wiki、任务元数据、OCR 提示词）的代码，优先放进 **`domain/<能力>/` 或命名明确的包**，而不是长期堆在泛化 `utils/`。

3. **横切能力单点维护**  
   凡多处复用的「字符串/规则/解析」**（如 OCR 提示词、页码规格解析）** 集中一处，通过 **显式函数**（如 `build_vision_ocr_prompt`）暴露，禁止复制粘贴大段 prompt。

4. **单向依赖**  
   `domain` → 不依赖具体路由；`api` → 可依赖 `domain`。避免 `domain` import `api`（防止循环与不可测）。

### 2.2 前端

5. **组件分层**  
   - **展示/交互 primitives**：按钮、表单区、步骤标题、无业务含义的布局。  
   - **feature**：某条业务线（如 PDF 阅读）的页面壳 + **hooks**（请求、状态机、与后端契约）。  
   - **页面**：组合 feature，保持薄。

6. **API 调用集中**  
   按资源或领域维护 `api/*.js`（或 ts），统一错误解析、base URL 约定；页面内避免散落裸 `fetch`。

### 2.3 契约与多端

7. **真相来源在后端或共享 schema**  
   任务 `metadata` 的枚举、必填、默认值：以后端校验与 `get_available_task_types` 输出为准；条件允许时生成或导出 **JSON Schema / OpenAPI 片段** 供前端与 CLI 对齐。

8. **CLI 与 UI 行为对齐**  
   同一操作路径下，校验失败信息、字段含义与后端一致；优先 **调用同一校验路径** 或同一 schema，避免 CLI 另写一套规则。

### 2.4 测试与重构节奏

9. **先抽再拆**  
   从重复逻辑抽 **纯函数/小模块** 并补测试，再动文件结构或大块拆分，降低一次性大爆炸。

10. **每抽一块补测试**  
    新公共模块至少覆盖：主路径、边界、与后端等价的关键用例（例如页码解析与 Python 一致）。

## 3. 清单（可随 PR 勾选）

### 3.1 后端 — 新建或移动代码时

- [ ] 新能力是否有 **唯一明确的包/模块路径**，避免「随手放进 `utils`」。
- [ ] `api` handler 是否 **≤ 若干屏幕**，复杂流程已下沉到 **domain/service**。
- [ ] 是否与 **另一入口**（任务队列、CLI、脚本）共享规则；若是，是否已 **复用同一模块**。
- [ ] 提示词、校验、解析是否 **无重复副本**（检索仓库内是否还有粘贴的重复段）。
- [ ] 新增环境变量或默认值是否在 **一处文档化**（可链接 `03-env-configuration.md` 或本 capability 设计小节）。
- [ ] 是否为公共逻辑补了 **单元测试**（不依赖完整 HTTP 栈为佳）。

### 3.2 后端 — 重构既有大块时

- [ ] `task_handlers`（或同类巨文件）是否按 **任务类型** 或 **阶段**（解析 → 抽取 → 后处理 → 写入）物理拆分，且 **对外行为不变**。
- [ ] 拆分后是否用 **现有集成测 / 手工用例** 回归关键任务类型。
- [ ] 是否避免引入 **api ↔ domain 循环依赖**。

### 3.3 前端

- [ ] 超长页面是否拆出 **hooks**（数据与状态机）与 **无业务 UI 子组件**。
- [ ] 同一 API 路径是否在 **一处** 封装，错误与 `detail` 处理一致。
- [ ] 与后端 **枚举/字段** 是否一致（必要时对照 `task-types` 或设计文档）。
- [ ] 新交互是否在 **任务/设置** 类页面遵循既有 **TaskForm / PageHeader** 等模式。

### 3.4 契约与多端一致

- [ ] 新 metadata 字段是否已进入 **后端 schema** 与 **校验**。
- [ ] 前端表单是否由 **schema 驱动** 或显式同步，避免「只后端有、UI 无」。
- [ ] CLI 若有对应子命令，是否使用 **同一校验/同一错误语义**（或文档注明暂时不对齐的原因）。

### 3.5 文档与可发现性

- [ ] 新公共模块是否在 **本目录 `README.md`** 或能力设计文档中有 **一句索引**。
- [ ] 破坏性变更是否更新 **changelog / 迁移说明**（若项目有约定）。

## 4. 反模式（应避免）

- 在多个路由或前后端 **复制同一段 prompt / 正则 / 页码解析**。
- 在 **`utils` 中堆砌** 仅被单一业务使用、且命名无法体现业务的模块。
- **巨型 handler / 巨型页面**：单文件承担 I/O、编排、业务规则与 UI 状态。
- **无契约的「约定」**：仅靠口头或注释对齐 CLI 与 Web 字段，而不以后端或 schema 为锚。
- **先改目录再改逻辑**：大搬家无测试，难以用 diff 证明行为等价。

## 5. 与现有实践的对应示例

- **视觉 OCR 提示词**：`backend/utils/vision_ocr_prompts.py` + `build_vision_ocr_prompt`，供 `web_reader` 与 `pdf_vision_extract` 共用（符合 §2.1.3、§3.1）。
- **任务 metadata**：以 `task_handlers.TASK_TYPES` 与校验函数为后端真相来源（符合 §2.3.7）。

后续若引入 `backend/domain/pdf/` 等目录，可在本文件 §5 追加「目录映射表」一行链过去即可。
