# 首页简报 / 研判报告 — 专用 Agent 设计方案

**文档类型**：01X 系统组件 / 产品 + 技术设计  
**状态**：**P0 + P1（部分）已落地** — P0：`home_briefing_report` + `GET/POST /api/home-briefing/*` + 首页 Markdown；P1（部分）：`GET /home-briefing/latest` 聚合最近任务（含失败/排队）、失败时仍展示**上一期成功**正文 + 琥珀提示；首页生成后**轮询** `/api/task-queue/tasks/{id}` 直至终态；**未做**：定时调度、导出 Markdown、构建进度 SSE 等（仍属 P1/P2 表内项）  
**时间**：2026-03-21  
**更新时间**：2026-03-13（P1 降级与轮询落地说明）；2026-03-21（纳入评审补强：一致性、降级、性能、进度、运维、风险）  
**范围**：定义独立于「任务列表数据视图」的**专用 Agent**，产出**叙述型报告与分析**，供首页主展示；系统健康、失败率、审计类信息**不纳入**本 Agent 主叙事（归属统计/审计页）。

---

## 1. 背景与定位

### 1.1 问题

- 当前首页偏「任务集合与状态」展示，偏**数据与运维视角**。
- 用户更关心 **AI 任务抓到的内容**经提炼后的**报告与分析**（如资讯研判、天气与出行含义、专题归纳），而非原始条目堆砌。
- **系统是否正常、队列是否堆积**等应放在**统计 / 审计**页面，避免与「读报告」心智混杂。

### 1.2 定位一句话

**首页核心 = 一篇可读的「简报/研判」文档；专用 Agent = 只负责在既定事实包上写报告与分析，不替代抓取任务、不承担系统运维叙事。**

### 1.3 与「普通对话 Agent」的边界

| 维度 | 通用对话 / 工作助手 | 本专用 Agent |
|------|---------------------|--------------|
| 入口 | 用户多轮提问 | 定时 / 事件 / 显式「刷新报告」 |
| 输出 | 随对话流变 | **版本化报告**（可对比上期） |
| 依据 | 广谱上下文 | **受限事实包**（来自指定任务类型与窗口） |
| 目标 | 解决问题、执行工具 | **归纳、对比、解读、局限说明** |

## 2. 目标与非目标

### 2.1 目标

| ID | 目标 | 说明 |
|----|------|------|
| G1 | **叙述型首页** | 首页主区域以**长文报告**（Markdown/富文本）为主，而非卡片信息流。 |
| G2 | **分析而不仅是摘要** | 含执行摘要、主题归纳、**交叉与矛盾**、**本期局限**；可选「相对上期的变化」。 |
| G3 | **可追溯** | 报告元数据与正文可关联到**任务 id、时间范围、来源链接**（折叠「依据」区，不抢主叙事）。 |
| G4 | **专用 Agent** | 在架构上为**独立 agent 或独立技能 + 固定编排**，便于配置模型、提示词、调度与观测。 |
| G5 | **与任务体系集成** | 输入来自任务队列/结果存储；可**由调度或上游任务完成事件触发**再生成。 |

### 2.2 非目标（本阶段）

- 在首页展示系统失败率、API 错误栈、队列深度（→ **审计/统计页**）。
- 自动执行高风险动作（重试任务、改配置、对外发帖）；本 Agent **默认只读分析**。
- 替代各垂直抓取任务；抓取仍由**既有 task_type** 完成，本 Agent **消费其结果**。

## 3. 专用 Agent 定义

### 3.1 名称（建议）

- 内部代号：**`home_briefing_agent`** 或 **`briefing_report_agent`**。
- 用户可见：**「简报」** / **「研判」**（产品文案可再定）。

### 3.2 职责（必须）

1. **接收事实包（Fact Pack）**  
   - 结构化 JSON：时间窗、条目列表（标题、摘要、来源 URL、任务 id、`task_type`、严重级别等）。  
   - 事实包由**上游构建器**生成（规则 + 可选轻量 LLM 抽取），**本 Agent 不直接爬网**（第一期）。

2. **生成报告正文**  
   - 按**固定章节模板**输出 Markdown（见 §4），强调**论点 + 依据引用占位**（与事实包 id 对应）。

3. **输出元数据**  
   - `generated_at`、`window_start` / `window_end`、使用的事实包版本、`model_id`（可选）、`prompt_version`。

### 3.3 职责（可选 / 二期）

- **对比上期**：输入带上期报告摘要或结构化 diff 要点，输出「相较昨日/上周的变化」小节。
- **多步自检**（agent 形态加强）：生成后第二次调用做「幻觉检查」——逐条核对是否超出事实包（仅标记风险句，不自动改文，或自动修订一版）。

### 3.4 明确不做

- 不作为用户随意聊天的入口（避免与通用对话抢上下文）。
- 不主动调用浏览器/搜索扩充事实（除非产品单列「研判前取证」阶段并单独审计）。

## 4. 报告结构（合同）

以下为 **v1 建议固定模板**，便于前端渲染与回归测试。

### 4.1 页眉（元数据区，非 LLM 自由发挥）

- 报告标题：如「简报 · 2026-03-21 晨间」  
- 覆盖时间范围、生成时间、事实条目数  

### 4.2 正文章节（LLM 生成）

1. **执行摘要**（约 10～28 行，视素材量；`prompt_version` v2 起强调信息密度）  
   - 结论与判断为主，但应**带入事实包中的具体要点**（机构、数据、引述），避免空泛一句带过。  
   - **含 `url` 的事实**：正文中须出现 `[锚文](url)` 与 `[Fx]`，主要可读入口在正文，文末「事实索引」仅作补充（实现见 `report_generate.SYSTEM_PROMPT` v2）。  

2. **分主题分析**  
   - 按**配置的主题**或**自动聚类**（如宏观 / 行业 / 本地天气与出行 / 用户订阅专题）。  
   - 每节：论点 → 支撑（引用 `[F1]、[F2]` 对应事实包 id）。  

3. **交叉与矛盾**  
   - 不同来源是否冲突；哪边更可信或需保留不确定性。  

4. **本期局限**  
   - 数据覆盖范围、缺失类型、未验证信息。  

### 4.3 附录（可由系统拼接，不必全文 LLM）

- **事实索引表**：id → 标题、链接、任务 id、抓取时间。  

### 4.4 输出 Schema（建议）

```json
{
  "schema_version": "1",
  "meta": {
    "title": "简报 · 2026-03-21 晨间",
    "window_start": "2026-03-20T16:00:00Z",
    "window_end": "2026-03-21T00:00:00Z",
    "generated_at": "2026-03-21T00:05:00Z",
    "fact_pack_version": "sha256:...",
    "agent": "home_briefing_agent",
    "model": "optional-model-id",
    "prompt_version": "v1"
  },
  "markdown": "# 执行摘要\n...",
  "fact_refs": [{ "id": "F1", "task_id": "...", "task_type": "...", "title": "...", "url": "..." }]
}
```

持久化时可拆表：`report` + `fact_pack`；首页只读最新 `report` 或按版本列表浏览。

## 5. 事实包（Fact Pack）构建

### 5.1 输入来源

- 任务队列 API：指定 **`task_type` 白名单**（如 `ai_news`、`weather_alert`、未来扩展）+ **时间窗** + **状态=已完成**。  
- 从 `result` / `result_summary` 中按 **per-type 映射**抽取字段（需在各 task handler 或统一 adapter 中约定最小 schema）。

### 5.2 最小条目字段（建议）

| 字段 | 说明 |
|------|------|
| `id` | 事实包内唯一，如 F1、F2 |
| `task_id` | 可追溯 |
| `task_type` | 分类与排序权重 |
| `captured_at` | ISO8601 |
| `title` | 短标题 |
| `summary` | 一两句客观摘要（可由抓取任务或规则预填） |
| `url` | 可选 |
| `severity` | 可选：`info` / `watch` / `alert`，用于排序与 UI 高亮 |

### 5.3 与 Agent 的衔接

- **第一期**：Fact Pack **纯规则/代码构建**，Agent **只消费** JSON + 模板提示词。  
- **第二期**：允许对每条 `summary` 做轻量 LLM 压缩，仍写入 Fact Pack 后再送报告 Agent（职责分离）。

### 5.4 并发与数据一致性（评审补强）

**问题**：同一窗口内多条抓取任务陆续完成，Fact Pack 构建与报告任务排队可能交错。

**建议策略**：

| 策略 | 说明 |
|------|------|
| **快照版本** | 报告任务启动时**冻结**一份 Fact Pack（不可变 blob + `fact_pack_version` 哈希）；生成全程只读该快照。 |
| **单调窗口** | 每次定时/事件生成使用明确 `[window_start, window_end)`，避免「边写边读」同一游标。 |
| **单写者** | 同一「简报产品线」同一时刻**最多一个** `home_briefing_report` 运行中；新触发若已有 running 则合并为「待处理一次」或丢弃重复（可配置）。 |

不强制全局锁死所有抓取任务；仅约束 **简报链路** 的 Fact Pack 与报告版本一一对应。

### 5.5 上游抓取异常与关键任务缺失（评审补强）

- **部分 task_type 失败或无完成记录**：Fact Pack 仍生成，在条目中可带 `source_status: missing|failed`（可选字段）；**强制**在报告模板中反映为「本期局限」或「某类数据未更新」，禁止模型假装已覆盖。  
- **关键类型全失败**（若配置「关键源」列表）：可不调用 LLM 全文生成，仅输出**短说明** + 链到任务列表/审计；或生成仅含「数据不可用说明」的一页（产品可选）。  
- **敏感信息**：见 §9.1；与抓取侧脱敏策略一致，Fact Pack 构建阶段**最后一道过滤**。

## 6. 触发条件与调度

| 触发 | 说明 | 建议 |
|------|------|------|
| **定时** | 如每日 08:00、20:00 | 服务端调度（与现有任务调度器对齐） |
| **事件** | 某类任务批量完成 | 防抖：N 分钟内合并一次生成 |
| **手动** | 用户点「重新生成简报」 | 显式调用，可突破短节流 |
| **进入首页** | 仅拉取**已生成**最新报告 | 默认**不**每次打开都打 LLM；可选「Stale 则后台排队」 |

**节流**：同一用户 / 全局维度 `min_interval`（如 15～30 分钟）避免重复全文生成。

### 6.1 时效性与突发（评审风险缓解）

- **固定时间窗**可能错过窗口刚结束后的突发要闻：可选 **「补充触发」**——某 `task_type` 产出带 `severity: alert` 且时间在窗外 N 分钟内时，**不立刻全文重写**，而是：进入 **下期 Fact Pack 优先队列** 或 **仅推送一条短讯**（二期）；避免每小时全文重跑。  
- 产品可配置：**每日主报告 + 告警类独立通道**（仍属「内容侧」，非系统运维）。

## 7. 首页页面设计（信息架构）

### 7.1 主区域

- **默认**：展示**最新一期**完整报告（Markdown 渲染），阅读型布局（适当最大宽度、字号）。  
- **次要**：版本切换（昨日/前次）或「与上期对比」入口（二期）。

### 7.2 辅助区域

- **依据**：折叠面板，展示事实索引或跳转任务详情。  
- **操作**：「重新生成」「订阅推送」（后期）。  
- **系统状态**：**不出现**大段运维信息；至多页脚一行链接「运行与审计 →」。

### 7.3 与任务列表关系

- **任务列表**降为二级入口（侧栏 / Tab「全部任务」），或从首页底部「查看相关任务」进入。  
- 首页**不以任务表格为主**。

### 7.4 报告生成进度反馈（评审补强）

- 简报以**任务类型**落地时，复用任务 **状态 / 进度**（如 `queued` → `running` → `completed|failed`）；首页「重新生成」进入后展示**进度条或阶段文案**（如「正在汇总事实 → 正在生成分析」）。  
- **长报告 / 慢模型**：可选 **SSE 流式**写入草稿区（实现成本较高，放 P1/P2）；P0 至少 **轮询任务状态 + 预计时间提示**。  
- 失败时：**明确错误摘要**（非技术栈），链到审计/任务详情给高级用户。

### 7.5 主题权重与个性化（评审补强，偏 P2）

- **配置层**：为各 `task_type` 或主题标签配置 **权重**（影响排序与报告内篇幅提示，仍由提示词约束 LLM）。  
- **UI**：设置页「简报偏好」：关注主题开关、是否弱化某类资讯（不删除事实，仅在分析中降权）。  
- **与事实包关系**：个性化只影响 **报告生成参数**，不篡改原始 Fact Pack 存档（便于审计对照）。

### 7.6 导出与分享（评审补强，初规）

- **导出**：P1 起支持 **Markdown / PDF** 下载（服务端渲染或浏览器打印）；文件含水印或生成时间。  
- **分享**：P2 可评估「只读链接」（需鉴权与过期策略）；**默认不**生成公开互联网链接。  
- **版权与外链**：导出物保留事实索引与来源 URL，免责声明可页脚固定文案。

## 8. 技术集成要点（实现时）

### 8.1 与现有编排的关系

- **方案 A**：注册为 **独立 Agent 类**，由调度器或 API handler 调用 `run(fact_pack) -> ReportArtifact`。  
- **方案 B**：**任务类型** `home_briefing_report`，与其它任务一致入队，结果即报告 JSON + markdown（便于审计与重跑）。  

推荐 **方案 B** 与现有 **任务管理/审计** 一致；首页仅消费「该类型最新成功结果」。

### 8.2 API 草图（实现时细化）

- `GET /api/home-briefing/latest` → 最新报告 + meta（无则 404 或空状态引导）。  
- `POST /api/home-briefing/generate` → 手动触发（鉴权、节流）。  
- 或统一走任务队列：`POST /api/task-queue/tasks` + `task_type: home_briefing_report`。

### 8.3 模型与配置

- 独立 **模型配置项**（可与写作/通用分离），便于用「长上下文、偏叙述」模型。  
- **提示词版本**与 **Fact Pack schema 版本** 写入 meta，便于回归。

### 8.4 报告生成失败降级（评审补强）

| 场景 | 行为 |
|------|------|
| 本次 LLM 或任务失败 | **保留展示上一期成功报告**；顶栏提示「本期简报生成失败，以下为上一期（时间戳）」。 |
| 尚无历史成功报告 | 空状态 + 「去完成任务 / 检查配置」引导；**不**白屏、不静默失败。 |
| 部分章节失败（若未来拆步） | 降级为「仅摘要 + 局限说明」或重试单次全文（可配置）。 |

### 8.5 大规模事实与性能（评审补强）

- **上限**：Fact Pack 条目数硬上限（如 200～500）+ **按 severity / 时间**截断；超出部分在「局限」中声明「另有 N 条未纳入」。  
- **预聚合**：高频类型先在构建器侧 **合并同类短讯** 再进包，减少 token。  
- **分块生成**（P2）：超大包时按主题分块调用 LLM 再合并，需注意 **交叉矛盾** 节的一致性，成本与延迟更高。  
- **缓存**：同一 `fact_pack_version` **不重复**调用同提示词全文生成（除非手动强制）。

### 8.6 多报告类型扩展（评审补强）

- **命名空间**：`report_kind`（如 `morning_briefing`、`weekly_digest`）+ 独立模板与调度；共用 Fact Pack 构建器但 **参数不同**（时间窗、task_type 白名单）。  
- **首页**：默认一种 `report_kind`，切换 Tab 或下拉可选其它类型（产品决定）。

## 9. 安全与合规

- 报告仅基于事实包；提示词中强制 **「不得编造事实包中不存在的来源与数据」**；保留「本期局限」节。  
- 对外链接默认 `rel="noopener noreferrer"`；敏感任务结果脱敏规则与全局审计策略一致。  
- 用户可见报告与内部日志区分存储级别。

### 9.1 敏感信息过滤（评审补强）

- **构建 Fact Pack 时**：对 `title`/`summary`/URL 参数做规则与可选模型辅助检测（密钥、身份证、手机号模式等）；命中则 **脱敏占位** 或 **整条条目不进入用户可见包**（审计侧可保留分级日志策略，与全局一致）。  
- **报告正文**：提示词要求不得展开已脱敏 token 的真实值。  
- **多租户/多用户**（若未来有）：Fact Pack 与报告 **按用户或工作区隔离**，防止任务结果串包。

## 10. 运维监控与质量（评审补强）

### 10.1 指标建议

| 指标 | 用途 |
|------|------|
| 生成 **延迟**（P50/P95） | SLA 与模型/分块策略优化 |
| **成功率**（任务 completed / failed） | 告警与降级是否生效 |
| **事实引用覆盖率**（可选，P2） | 抽样或规则：正文中 `[F*]` 与 `fact_refs` 可解析比例 |
| **token 用量 / 调用成本** | 预算与上限 |

### 10.2 存储与成本

- 报告 + Fact Pack **保留策略**：如保留最近 K 期全文 + 更早仅 meta；可配置 TTL。  
- 大正文 **压缩存储**（gzip）或对象存储外链（实现时选型）。  
- 定期归档与审计表对齐，避免无限增长。

## 11. 已知风险与缓解（评审汇总）

| 风险 | 缓解 |
|------|------|
| 关键任务未完成导致报告偏空 | §5.5 局限声明 + 可选不生成全文；首页展示上期 |
| 固定窗错过突发 | §6.1 补充触发 / 告警通道 |
| LLM 不稳定（超时、限流） | 重试与退避；§8.4 降级；监控 §10.1 |
| 幻觉 | 事实包约束 + 「本期局限」+ P2 自检 |
| 事实包不完整仍强行分析 | 提示词与模板强制「不得推断未提供数据」 |

## 12. 分期落地建议

| 阶段 | 内容 |

## 13. 验收标准（设计层）

- 首页首屏主体为**报告正文**，而非任务表。  
- 任意结论可在**依据区**找到对应任务/来源或明确标为推断。  
- 系统类指标不在本页展开，**审计页**可单独完善。  
- 本期生成失败时，用户仍能看到**上一期**或明确空状态，而非解析错误或白屏（与评审一致）。
