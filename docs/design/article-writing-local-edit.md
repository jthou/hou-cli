# 写文章：局部修改（在指定位置插入/替换）— 设计方案

## 一、需求与现状

### 1.1 典型场景

用户希望**只改文章的一处**，其余保持不变。例如：

- 在「01 实战迭代：AI的战争学习曲线」中，在「三个铁证表明AI已深度参战」列表**之后**插入一段新证据；
- 或替换某一小节中的某一段落，其它章节不动。

当前文章以**整篇 Markdown 字符串**存储，修改方式只有两种：

- **接受修改**：用某条助手回复的**全文**替换整篇 `current_article`；
- **恢复版本**：用历史某次**全文**作为当前文章。

因此，要实现「在 01 节某处插入一段，其余不变」，目前只能：

- 让助手生成**整篇修改后的文章**，用户再点「接受修改」整篇替换；或
- 用户自己复制全文 → 在别处编辑 → 再整篇贴回（无专门 UI/API 支持）。

前者依赖模型输出整篇，耗 token、且可能改动无关部分；后者体验差、易出错。

### 1.2 设计目标

- 支持**局部修改**：在「某节 / 某段 / 某锚点后」插入或替换内容，其余部分不变。
- 与现有「整篇替换 + 历史版本」兼容，不破坏已有接受修改、恢复版本流程。
- 局部修改结果仍作为新版本入库，可追溯、可恢复。

---

## 二、方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 仅整篇替换（现状）** | 用户发指令 → 助手输出整篇修改文 → 用户「接受修改」 | 已实现，无需改存储 | 耗 token；模型可能改错别处；长文时体验差 |
| **B. 锚点式局部编辑** | 用户/助手提供「锚点」（如某段首句或小节标题）+ 新内容；后端在正文中查找锚点，在其后插入或替换一段 | 只改一处，其余不动；实现相对简单；仍存为整篇 Markdown | 锚点匹配需策略（精确/模糊/首次）；多匹配时需约定 |
| **C. 按节结构化存储** | 文章按「节」存储（如 JSON：sections: [{title, content}]），编辑时按 section_id + 段落索引操作 | 语义清晰，可做「编辑本节」UI | 需迁移现有平铺 Markdown；与现有预览/导出要统一 |
| **D. 差分/补丁** | 用户提供「旧片段 → 新片段」或 diff；后端在正文中查找并替换 | 精确替换，适合「改一句话」 | 旧片段必须完全一致；空格/换行敏感；插入需额外语义 |

**推荐**：先做 **B. 锚点式局部编辑**，在不大改存储和前端的前提下支持「在某某之后插入 / 替换这一段」，并与现有整篇替换、历史版本并存。

## 三、推荐设计：锚点式局部编辑

### 3.1 概念

- **锚点（anchor）**：当前文章中的一段**唯一或可唯一定位**的文本，用于确定「插入位置」或「被替换的段落」。例如：
  - 小节标题：`## 01 实战迭代：AI的战争学习曲线`
  - 或某段首句：`**三个铁证表明AI已深度参战：**`
- **局部操作**：
  - **insert_after**：在锚点**首次出现位置之后**插入一段内容（不删除原有内容）；
  - **replace_after**（可选）：在锚点之后用新内容**替换**紧接着的 N 段或到下一标题为止（需约定范围）。

先实现 **insert_after** 即可覆盖「在 01 节某段后加证据」的需求；replace 可二期再做。

### 3.2 后端 API

**新增**：`POST /api/chat/article/patch`（或 `/api/chat/article/local-edit`）

请求体示例：

```json
{
  "session_id": "xxx",
  "op": "insert_after",
  "anchor": "**三个铁证表明AI已深度参战：**",
  "content": "**最新证据揭示AI作战的复杂博弈：**\n当地时间2月28日美军对伊朗实施军事打击期间……"
}
```

响应：

```json
{
  "status": "success",
  "article": "整篇修改后的文章内容（Markdown）"
}
```

若未找到锚点或匹配不唯一，返回 4xx 或 `status: "error"`，并带 `error` 说明（如 "锚点未找到" / "锚点匹配到多处"）。

**逻辑概要**：

1. 用 `session_id` 取当前文章 `current_article`（来自 `article_revisions` 或现有 storage）。
2. 在 `current_article` 中查找 `anchor`：
   - **精确匹配**：`anchor in content`，取第一次出现位置；
   - 或 **行级匹配**：按行切分，找到首行包含 `anchor` 或 trim 后等于 `anchor` 的行，再在该行结束位置后插入。
3. 在锚点**之后**插入 `content`（可约定插入时前后各加一个 `\n\n`，保证段落分隔）。
4. 将得到的新全文作为新版本写入 `article_revisions`（`source='user'`），并更新 `current_article` 与 `current_article.md`。
5. 返回新文章全文，前端刷新预览并可选刷新历史版本列表。

**锚点匹配策略（可配置或先写死）**：

- 优先：整段或整行包含 `anchor` 的**第一次**出现；
- 若 `anchor` 在文中有多处，可返回错误提示用户缩小锚点（如用更长的一段话），或支持可选参数 `which: "first" | "last" | "all"`（首版先做 first）。

### 3.3 与对话的配合方式

两种用法，可并存：

**方式 1：用户在前端做「局部插入」**

- 在文章预览或历史版本旁增加「**在指定位置插入**」入口（如按钮 + 弹窗）。
- 用户输入或选择「锚点」（可从当前文章中选一段作为锚点，或手动输入），再输入要插入的段落；提交后调用 `POST /api/chat/article/patch`，用返回的 `article` 更新预览并刷新历史版本。

**方式 2：助手在对话中返回「结构化局部编辑」**

- 用户发：「请在 01 实战迭代 中、三个铁证 那一段后面插入以下证据：……」
- 助手在流式回复中**同时**（或仅在内部）产出可被前端/后端识别的「局部编辑」结构，例如：
  - 在回复末尾附带一行约定格式（如 `__ARTICLE_PATCH__:{"op":"insert_after","anchor":"...","content":"..."}`），前端解析后自动调 `patch` API；或
  - 助手只输出「已插入」的整篇修改文，用户点「接受修改」整篇替换（保持现有逻辑）。

推荐**首版只做方式 1**（用户主动在前端做锚点插入），避免解析助手输出的复杂度和歧义；方式 2 可作为后续增强（例如助手返回建议的 anchor + content，由用户确认后调 patch）。

### 3.4 前端交互（方式 1）

- **入口**：文章预览区域标题栏或操作栏增加「**局部插入**」按钮。
- **弹窗**：
  - **锚点**：输入框（可支持从当前文章中勾选一段作为锚点粘贴进来），或下拉选择「常用锚点」（如各小节标题，由前端从当前文章解析 `##` 得到）。
  - **要插入的内容**：多行文本框，支持 Markdown。
  - **提交**：调用 `POST /api/chat/article/patch`，成功后刷新预览与历史版本列表，关闭弹窗。
- **错误**：锚点未找到或匹配多处以 toast 提示，并可在弹窗中保留已填内容便于修正。

### 3.5 历史版本与审计

- 每次 `patch` 产生的新全文，与现有「接受修改」一样，作为一条新记录写入 `article_revisions`，`source='user'`（或单独 `source='patch'` 便于区分）。
- 历史版本列表与恢复逻辑不变：恢复的仍是「某次完整文章快照」，不区分该次是整篇替换还是局部编辑得到的。

## 四、当前设计能否处理「你给的这篇局部修改」？

- **若只依赖现有能力**：可以，但需要**整篇**替换。即由助手生成「从标题到 01 节插入新段落后」的**完整文章**（你给的从 `# AI军备竞赛` 到 `---` 及「后续章节保持不变」的完整版），用户对这条助手回复点「接受修改」，即可得到你期望的效果。缺点：模型必须输出整篇，且可能动到其它段落。
- **若采用本设计的「锚点式局部编辑」**：可以更精准地处理。用户（或后续的助手辅助）提供：
  - **anchor**：例如 `**三个铁证表明AI已深度参战：**` 或到列表结束的某段唯一文本；
  - **content**：你给出的「**最新证据揭示AI作战的复杂博弈：** 当地时间2月28日……」整段。
  调用 `insert_after` 后，后端只在锚点后插入该段，其余原样保留，且自动形成新版本，无需整篇重写。

---

## 五、实施顺序建议

1. **后端**：实现 `POST /api/chat/article/patch`（`op: insert_after` + `anchor` + `content`），锚点首次匹配 + 插入后写回 `article_revisions` 与 `current_article`。
2. **前端**：在文章预览区增加「局部插入」入口与弹窗，调用 patch API 并刷新预览与历史版本。
3. **可选**：从当前文章中解析 `##` 标题，作为「锚点」快捷选项；或支持在预览中选中一段作为锚点。
4. **可选二期**：`replace_after`（替换锚点后一段）、或助手返回建议的 patch 由用户确认后执行。

按此设计，你描述的「在 01 实战迭代 中 三个铁证 后插入证据、其余不变」即可由系统直接、可靠地完成，且与现有整篇替换和历史版本兼容。
