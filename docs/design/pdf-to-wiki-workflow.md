# 设计：PDF 下载 → 拆分 → 转文字 → 翻译 → 写入 MediaWiki

## 1. 目标与范围

### 1.1 目标

- **输入**：PDF 的 URL（如 `https://example.com/doc.pdf`）或本地文件路径。
- **输出**：将 PDF 内容提取为文本、按目标语言翻译、写入 MediaWiki；支持**超大文件**（如整本书）通过「拆分 → 分批处理」完成。
- **与 web_fetch 的关系**：**不复用** web_fetch。PDF 体量、格式与风险与网页正文不同，单独实现「PDF 专用」流水线，避免大文件拖垮通用抓取工具。

### 1.2 范围

| 在范围内 | 不在范围内（后续扩展） |
|----------|------------------------|
| 单次任务处理一个 PDF（URL 或本地路径） | 批量「多个 PDF 一次提交」 |
| 按页/按块拆分、逐块转文字与翻译 | 按 PDF 书签/目录自动识别章节（可后续增强） |
| 写入策略：单页汇总 或 多子页面（可选） | 断点续传、任务暂停/恢复（可后续增强） |
| 文件大小与页数上限、超时与错误处理 | 实时流式下载（当前为整文件下载后处理） |

---

## 2. 流程总览

整体流水线（严谨顺序）：

```
[输入] PDF URL 或 本地路径
    ↓
① 下载（若为 URL）→ 落盘到临时文件，校验 Content-Length / 文件大小
    ↓
② 校验：文件大小 ≤ 上限、页数 ≤ 上限（可选），超限则拒绝并提示
    ↓
③ 拆分：按「块」划分（见 4. 拆分策略），得到 N 个「块」
    ↓
④ 转文字：对每个块提取文本（按页范围或字节范围读取），得到 N 段纯文本
    ↓
⑤ 翻译：对每段文本调用 LLM 翻译（可串行/并行，带进度），合并为完整译文
    ↓
⑥ 写入 Wiki：按「写入策略」生成 1 个或多个 Wiki 页面（见 5. 写入策略）
    ↓
[输出] 任务 result：成功/失败、写入的页面标题列表、可选错误明细
```

**原则**：先落盘、再按块处理，避免整本 PDF 常驻内存；单块文本长度受控，便于 LLM 与超时管理。

## 3. 限制与安全

### 3.1 配置

| 配置项 | 建议默认值 | 说明 | 配置方式 |
|--------|------------|------|----------|
| **单次任务总超时** | 60 分钟 | 任务级超时（含下载+拆分+转文字+翻译+写入） | `task_worker.TASK_TIMEOUT_SECONDS["pdf_to_wiki"]` |
| **单块最大字符数** | 8000 字符 | 每块转文字+翻译的文本上限，避免单次 LLM 过长 | 代码常量或配置 |
| **下载超时** | 300 秒（5 分钟） | 仅针对「下载」阶段 | 环境变量 `PDF_TO_WIKI_DOWNLOAD_TIMEOUT` |

### 3.2 安全与资源

- **临时文件**：下载的 PDF 仅存于任务临时目录，任务结束（成功/失败/超时）后**必须删除**，避免堆积。
- **并发**：同一 Worker 上可限制「同时进行中的 pdf_to_wiki 任务数」（如 1～2），避免多本大书同时占满内存与 CPU。

## 4. 拆分策略

### 4.1 目标

- 将 PDF 划分为多个「块」，每块**独立**：转文字 → 翻译，块与块之间无重叠。
- 单块文本长度 ≤ 单块最大字符数（如 8000），便于 LLM 单次调用与超时控制。

### 4.2 按「页」拆分（推荐）

- **单位**：页（由 PDF 解析库得到总页数，再按页范围切分）。
- **块大小**：每块包含 **固定页数**，如 10 页/块（或按「约 8000 字符」动态估算页数，但实现更复杂）；最后一块可不足 10 页。
- **优点**：边界清晰、不破坏段落（若一页内段落完整）。
- **实现**：用 pdfplumber / pypdf 按 `pages[from:to]` 提取文本，拼接为该块文本；若单块超过 8000 字符则再细分为更小页范围。

### 4.3 可选：按「章节」（后续扩展）

- 若 PDF 有书签/大纲（Outline），可按章节划分块；无书签时回退到「按页」拆分。
- 一期可不实现，仅预留「块类型：page_range | chapter」的扩展点。

### 4.4 块与进度的对应

- 每块对应一个「步骤」：转文字 → 翻译；任务进度可按「当前块序号 / 总块数」更新，便于前端展示「第 3/20 块翻译中」。

## 5. 写入策略（Wiki 输出形态）

### 5.1 策略 A：单页汇总（推荐用于文章/短文）

- **适用**：总页数较少（如 ≤ 50 页）或用户希望「一个 Wiki 页面」。
- **行为**：所有块翻译后**按顺序合并**为一段 wikitext，加上原文链接、分类等，写入**一个** Wiki 页面（如标题为「书名」或用户指定 `wiki_title`）。
- **结构**：正文前加「原文链接」；正文内可用 `== 第 1 部分 ==` 等小节标题区分原 PDF 的块；文末加分类标签。

### 5.2 策略 B：多子页面（推荐用于书籍）

- **适用**：总页数较多（如 > 50 页）或用户明确选择「按章节/部分分页」。
- **行为**：每个块对应一个 Wiki 子页面，如 `书名/第1部分`、`书名/第2部分`；再创建一个**目录页**（如 `书名`），内容为各子页面的链接列表 + 简介。
- **命名**：子页面标题可由用户指定前缀 + 块序号，或由「章节标题」（若未来支持）派生。

### 5.3 策略选择方式

- **metadata 参数**：如 `wiki_output_mode: "single" | "multi"`，默认 `single`。
- 或根据**页数/块数**自动选择：若块数 > 阈值（如 5）则建议用 `multi`，仍可由用户覆盖。

## 6. 失败与部分完成

### 6.1 单块失败

- **转文字失败**：该块标记失败，记录错误原因；可选择「跳过该块继续」或「整任务失败」。
  - 建议一期：**跳过该块**，继续后续块，最终结果中标记「第 N 块提取失败」，汇总页或子页面中该块位置留空或写「（本段提取失败）」。
- **翻译失败**：同上，该块可留原文或标记「翻译失败」，其余块照常写入。

### 6.2 任务级失败

- **下载失败**：任务直接失败，无部分结果。
- **页数/大小超限**：任务失败，返回明确错误码与提示。
- **写入 Wiki 失败**：若为单页模式，任务失败；若为多子页模式，可记录「已成功写入前 K 个子页，第 K+1 个写入失败」，便于人工补写或重试。

### 6.3 结果结构建议

```json
{
  "status": "success" | "partial" | "error",
  "summary": "已处理 18/20 块，成功写入 1 个 Wiki 页面（xxx）",
  "data": {
    "pdf_url_or_path": "...",
    "wiki_title": "主页面标题",
    "wiki_pages": ["主页面标题", "主页面标题/第1部分", ...],
    "total_chunks": 20,
    "successful_chunks": 18,
    "failed_chunks": [{"chunk_index": 3, "reason": "提取失败"}, ...]
  }
}
```

## 7. 任务类型与 API 设计

### 7.1 任务类型：`pdf_to_wiki`

- **name**：`PDF 转 Wiki`
- **description**：下载 PDF（或使用本地路径），按块拆分、转文字、翻译后写入 MediaWiki；支持大文件分块处理。

### 7.2 metadata_schema 建议

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `url` | string | 与 `file_path` 二选一 | PDF 的 http(s) URL |
| `file_path` | string | 与 `url` 二选一 | 本地 PDF 路径（如由上传接口得到） |
| `wiki_title` | string | 否 | 主 Wiki 页面标题；留空可由 PDF 元数据或文件名派生 |
| `language` | string | 否 | 目标语言，同 url_to_wiki：zh / en / ja，默认 zh |
| `wiki_output_mode` | string | 否 | `single`（单页汇总）\| `multi`（多子页面），默认 single |
| `categories` | array | 否 | 同 url_to_wiki，分类标签列表 |

### 7.3 与现有体系的关系

- **不复用** web_fetch：PDF 的下载、校验、拆分、转文字均在 pdf_to_wiki 任务内或专用「PDF 工具」中完成。
- **复用**：LLMService（翻译）、MediaWikiTool（写入）、任务队列与超时机制、前端任务创建/详情/结果展示（可复用 TaskResultDisplay 的扩展）。
- **不复用** url_to_wiki 的 handler：url_to_wiki 仅处理 HTML 页面；pdf_to_wiki 为独立 handler，内部调用「PDF 下载 + 拆分 + 转文字」逻辑后再调用 LLM + MediaWiki。

### 7.4 专用组件（建议）

- **PDF 下载**：独立函数或小模块，负责：GET 落盘、返回临时文件路径；失败时清理临时文件。
- **PDF 拆分与转文字**：输入临时文件路径 + 块大小，输出「块列表」每块为 `{ page_range: [from, to], text: str }`；依赖 pdfplumber 或 pypdf，按页读取，控制单块字符数上限。
- **任务 handler**：`process_pdf_to_wiki_task`：校验 metadata（url 或 file_path）→ 下载（若 URL）→ 拆分 → 逐块转文字 → 逐块翻译（带进度）→ 按写入策略写入 Wiki → 清理临时文件 → 返回 result。

## 9. 大文件执行形态：单任务内分块 vs 拆成多个子任务

大文件（如整本书）可按两种方式执行：**一个任务内部循环处理多个块**，或**一个主任务创建多个子任务、每块一个子任务**。本节对比两种方式，并说明当前任务体系若支持「子任务」是否别扭。

### 9.1 方案对比

| 维度 | 单任务内分块（推荐一期） | 拆成多个子任务 |
|------|--------------------------|----------------|
| **任务数量** | 1 个任务（pdf_to_wiki） | 1 个主任务 + N 个子任务（如 pdf_chunk_to_wiki #1..#N） |
| **执行方式** | Handler 内：下载 → 拆分 → for 块 in chunks { 转文字 → 翻译 } → 合并写入 | 主任务：下载 → 拆分 → **创建 N 个子任务**并入队 → 主任务结束；Worker 再逐个拉取子任务执行 |
| **进度** | `update_task_progress(percent, "第 3/20 块翻译中")`，一目了然 | 主任务很快结束；进度需看「子任务完成数 / N」或汇总展示 |
| **单块失败** | 可跳过该块、继续后续，最终 result 标记 partial + failed_chunks | 某子任务失败可单独重试，不影响其它子任务 |
| **断点续传** | 需在任务内自己做 checkpoint（如 result 存已完成的块索引），重试时跳过已完成的块 | 天然支持：未完成的子任务仍在队列，重跑即可 |
| **任务模型** | 无需改现有模型；仅一个任务类型、一个 handler | 需「主任务在 handler 内能创建任务」且子任务与主任务有关联（见 9.2） |
| **UI** | 任务列表只有 1 条，详情里看进度与 result | 任务列表出现 1 + N 条；需分组或折叠展示「主任务 + 子任务」 |
| **临时文件** | 主任务结束即删 PDF | 需等**所有子任务**完成后才能删 PDF；若某子任务一直不跑或失败，清理逻辑复杂 |

### 9.2 当前任务体系要支持「子任务」会怎样？

现有能力：

- **已有**：`depends_on_task_id` + `input_bindings` 表示「下游依赖上游、从上游 result 取输入」；`pipeline_id` 用于分组展示。
- **没有**：任务表无「父任务 ID」「子任务列表」；也没有「一个 handler 在执行过程中创建其它任务」的约定。

若采用「主任务 + N 个子任务」：

1. **主任务 handler 内创建任务**  
   - 主任务执行到「拆分完成」后，调用 `task_queue_db.create_task(...)` N 次，创建 N 个子任务；每个子任务带 `depends_on_task_id = 主任务 id`（或预留字段 `created_by_task_id`）。  
   - **问题**：当前 handler 是「执行完就返回」，没有「handler 可以创建任务」的官方用法；需要允许在 handler 内调用 create_task，且约定好权限与幂等（避免重复创建）。

2. **子任务拿什么输入？**  
   - **做法 A**：主任务不把块内容放进 result（避免 result 巨大），而是把「临时 PDF 路径 + 块索引 / 页范围」写入 result；子任务通过 `depends_on_task_id` + `input_bindings` 从主任务 result 里取本块的 page_from/page_to 和 temp_pdf_path。  
   - **做法 B**：主任务创建子任务时，直接把该块所需信息写入**子任务的 metadata**（如 temp_pdf_path、page_from、page_to、wiki_title_base）；子任务不依赖 input_bindings，只依赖「主任务已把 PDF 落盘」——即主任务先完成并写入 result（含 temp_pdf_path），子任务被拉取时可直接用自身 metadata，必要时从 result 读 temp_pdf_path 以校验文件存在。  
   - 做法 B 更简单，但要求主任务 result 至少包含 temp_pdf_path，且子任务运行前主任务已完成（否则依赖关系可设为「子任务 depends_on 主任务」，Worker 只在主任务完成后再拉子任务）。

3. **临时文件生命周期**  
   - 主任务完成后 PDF 仍在盘上；子任务逐个读该 PDF 做本块提取与翻译。全部子任务完成后谁删 PDF？可选：最后一个完成的子任务删除；或主任务 result 里记录「子任务 id 列表」，由定时清理任务在检测到「所有子任务都已完成/失败」后删。逻辑较啰嗦，且要处理「主任务失败/取消」时子任务与临时文件的清理。

4. **UI 与分组**  
   - 若增加 `created_by_task_id`（或统一用 `pipeline_id` 把主+子归为一组），列表可展示「PDF 转 Wiki (主)」下挂「#1..#N」；否则 N 条平铺，用户会看到很多「pdf_chunk_to_wiki」任务，容易困惑。

**结论（是否别扭）**：

- **会有一点别扭**：现有模型是「任务之间依赖 + 输入绑定」，没有「父创建子」的一等概念；要支持子任务就需要「handler 内创建任务」+ 临时文件与清理的约定 + 前端分组展示，都属于对现有体系的扩展而非直接复用。
- **不是做不到**：不一定要新增「子任务」表或大改模型；用「主任务创建 N 个 depends_on 自己的任务」+ 可选 `created_by_task_id`/`pipeline_id` 分组即可模拟，但实现和运维成本都更高。

### 9.3 推荐结论

- **一期（MVP）**：采用 **单任务内分块**。  
  - 一个 `pdf_to_wiki` 任务，handler 内顺序：下载 → 校验 → 拆分 → 逐块转文字 → 逐块翻译（带 `update_task_progress`）→ 合并写入 Wiki → 删临时文件。  
  - 不改任务模型，不引入「handler 创建任务」；大文件通过「块」控制内存与超时，通过进度文案让用户看到「第 k/N 块」。  
  - 若某块失败，可采用「跳过该块、继续后续、最终 result 标记 partial」；断点续传留到 Phase 3 用单任务内 checkpoint 实现。

- **后续若需「子任务」再扩展**：可采用下文 9.4 的「任务链表」模型，统一约定父子/链路与清理责任。

### 9.4 子任务抽象：任务链表（父子和链路关系）

若希望子任务成为体系内的一等概念，可把**子任务视为一条有上下游关系的任务链表**（可能有依赖，也可能没有依赖），而不是临时用「主任务创建 N 个 depends_on 自己」来凑。这样扩展更清晰，也便于复用（如其它「先分解再执行」的流水线）。

#### 9.4.1 链表语义

- **主任务**：只负责「分解」——下载/校验/拆分后，**创建并逐个入队** N 个子任务，主任务自身可立即完成（result 仅记录「已创建 N 个子任务」及 chain_id 等），不持有需长期保留的资源。
- **子任务**：链上的一环，每个子任务只做自己那一块（如：读 PDF 某页范围 → 转文字 → 翻译 → 写 Wiki 子页）；**可有依赖**（如依赖主任务 result 里的 temp_pdf_path），**也可无依赖**（主任务创建时把本块所需 metadata 直接写入子任务）。
- **最后一个任务**：链尾任务在**执行结束时负责清理资源**（如删除临时 PDF）。谁算「最后一个」由链路关系或元数据明确标识（见下）。

这样：主任务不入队大段计算，只做分解与入队；实际工作在子任务上；资源生命周期由「链尾任务」统一收口，不必再依赖定时清理或主任务 result 轮询。

#### 9.4.2 每个任务记录的父子/链路关系

在现有任务表上增加少量字段即可表达「链表」与「谁负责清理」：

| 字段 | 类型 | 说明 |
|------|------|------|
| `parent_task_id` | TEXT NULL | 若本任务是由某任务「分解出来的」，则指向该父任务；主任务此项为 NULL。用于 UI 分组、查询「某主任务下的所有子任务」。 |
| `chain_id` | TEXT NULL | 同一条链上的任务共用同一 chain_id（如 UUID）；主任务创建子任务时写入，便于按链查询、折叠展示。可与 `pipeline_id` 复用或替代。 |
| `chain_index` | INT NULL | 本任务在链中的序号（0-based）；主任务可为 0 或 NULL。 |
| `chain_total` | INT NULL | 本链子任务总数（不含主任务时为 N）。链尾判定：`chain_index == chain_total - 1`（若主任务不占序号）或由主任务在创建时给「最后一个」子任务打标记。 |
| `is_chain_tail` | BOOLEAN NULL | 若为 true，表示本任务为链尾，**执行完成后负责清理链上共享资源**（如 temp_pdf_path）。主任务创建子任务时对最后一个设置 true。 |

依赖关系可与链路并存但不强绑：

- **有依赖**：子任务可继续使用 `depends_on_task_id`（如依赖 parent）和 `input_bindings` 从父任务 result 取输入；适合「父任务把 temp_pdf_path、chunk 列表放进 result，子任务按 chain_index 取本块」。
- **无依赖**：父任务创建子任务时直接把本块所需信息写入子任务 metadata，子任务不依赖父任务 result；此时 `parent_task_id` / `chain_id` 仅用于归属与展示，Worker 拉取子任务时无需等父任务 result。

两种都可支持，按场景选：PDF 场景下父任务把 temp_pdf_path 放进 result、子任务用 `depends_on_task_id` + `chain_index` 取本块，或父任务创建时把 temp_pdf_path + page_from/page_to 写入每个子任务 metadata（无依赖）。

#### 9.4.3 资源清理约定

- **链尾任务**：在 handler 结束时检查 `is_chain_tail == true`（或等价：`chain_index == chain_total - 1`）；若为真，则读取链上约定好的资源句柄（如主任务 result 中的 `temp_pdf_path`，或 chain 级别存储在 result/DB 的路径），执行删除或回收。
- **主任务失败/取消**：若主任务在「创建子任务之前」失败，无资源可清；若主任务在「创建子任务之后」失败或取消，已入队的子任务可照常执行，由**链尾任务**在完成时清理；若希望「主任务取消则整链取消」，需调度层支持「按 chain_id 取消未执行的子任务」并在主任务取消时触发。
- **子任务失败**：链尾若未执行到（某中间子任务失败导致链尾未入队的情况不存在——所有子任务已入队），链尾仍会被 Worker 拉取并执行，可在链尾 handler 内做「无论本块成功与否都清理」的逻辑；若链尾任务本身失败，可退化为定时清理任务扫描「chain 上所有任务已终态且存在 temp_pdf_path」的链做清理。

#### 9.4.4 与现有体系的关系

- **兼容**：`depends_on_task_id` / `input_bindings` 保留；链表关系用 `parent_task_id`、`chain_id`、`chain_index`、`chain_total`、`is_chain_tail` 表达，不替代依赖，只补充「谁是谁拆出来的、谁收尾」。
- **handler 创建任务**：约定允许某类任务（如 pdf_to_wiki 主任务）的 handler 在完成「分解」后调用 `create_task` 创建子任务并写入上述链路字段；子任务类型可为专用（如 pdf_chunk_to_wiki）或与主任务同类型（由 metadata 区分角色）。
- **前端**：列表/详情按 `chain_id` 或 `parent_task_id` 分组，主任务下折叠展示「子任务 #1..#N」，链尾可标出「负责清理」；进度可汇总为「链上已完成数 / chain_total」。

这样，子任务就是「有父子/链路关系的任务链表」：主任务分解并入队，最后一个任务负责清理，每个任务都记录自己在链上的位置与是否收尾，既不依赖临时 hack，也为后续其它「分解+多步执行」场景留出统一模型。

## 10. 现有任务体系与新需求关系梳理及设计评估

### 10.1 现有任务管理体系摘要

| 维度 | 现状 | 依据 |
|------|------|------|
| **任务实体** | 单表 `tasks`：task_id、task_type、task_name、status、priority、metadata、result、progress、message、worker_id、created_at、started_at、completed_at、duration、error、retry_count、max_retries、updated_at | task_queue_db 建表与迁移 |
| **依赖与管道** | `depends_on_task_id`（上游唯一）+ `input_bindings`（上游 result → 本任务 metadata）；`pipeline_id` 仅分组展示 | task-pipeline-design.md |
| **拉取规则** | 仅当「无依赖」或「依赖任务已完成且 result 非空」时可被 acquire；同一队列内按 priority DESC、created_at ASC | task_queue_db acquire_task |
| **创建方式** | 用户/API 直接 `create_task`；定时任务由心跳在 `scheduled_tasks` 到点时调用 `create_task(..., created_by_schedule_id=...)` | task_queue_db、scheduled-tasks-implementation.md |
| **执行** | Worker 按类型调用已注册 handler；执行前若有 depends_on，则用上游 result 解析 input_bindings 并合并进 metadata | task_worker、pipeline_resolve |
| **父子/链** | **无** parent_task_id、chain_id、chain_index、is_chain_tail；**无**「handler 内创建任务」的约定 | 现有表结构及 Worker 逻辑 |

即：当前是「**用户/定时创建 → 入队 → 按依赖可执行后拉取 → 执行**」；依赖是「下游依赖上游、输入从上游 result 来」，没有「上游主动拆成多个下游」的语义，也没有「谁负责收尾清理」的约定。

### 10.2 新需求与现有体系的对应关系

| 新需求 | 与现有体系的关系 | 设计上的选择 |
|--------|------------------|--------------|
| **PDF 转 Wiki（单任务内分块）** | 新增任务类型 `pdf_to_wiki`，一个任务、一个 handler；内部「下载→拆分→逐块转文字→逐块翻译→写入」；不涉及「创建子任务」 | 完全落在现有模型内：新类型 + 新 handler + 超时配置；无表结构变更 |
| **PDF 转 Wiki（子任务/大书）** | 需要「主任务在 handler 内创建 N 个子任务并入队」；子任务需与主任务有父子/链关系；链尾负责清理 | 超出当前模型：需新增「链」相关字段与「handler 可创建任务」约定 |
| **任务链表（父/子/链尾）** | 提供「谁拆出来的、谁收尾」的一等表达，与 depends_on 并存 | 新增 parent_task_id、chain_id、chain_index、chain_total、is_chain_tail；与 pipeline_id 可共存或部分复用 |

### 10.3 一致性检查

- **单任务内分块（一期）**  
  - 与现有「一个任务一个 handler、不创建任务」完全一致；与 `depends_on_task_id` / `pipeline_id` 无冲突；定时任务、队列、进度、失败重试均沿用现有逻辑。  
  - **结论**：一致，无需改表或 Worker 契约。

- **任务链表（后续扩展）**  
  - **与 depends_on 的关系**：链表表达「谁是谁拆出来的、谁收尾」；依赖表达「谁要等谁、输入从哪来」。子任务可以既 `parent_task_id = 主任务` 又 `depends_on_task_id = 主任务`（等主任务 result 再跑），也可以仅 `parent_task_id` 设置、metadata 已带齐（无依赖）。  
  - **与 pipeline_id 的关系**：同一条链可共用 `chain_id` 做分组；`pipeline_id` 当前是「用户创建管道时」打的组号，链是「主任务创建子任务时」打的组号，可并存（链用 chain_id，管道用 pipeline_id），或约定「链场景下用 chain_id 替代 pipeline_id 做分组」以少一个字段。  
  - **acquire 逻辑**：无需改。子任务若有 depends_on_task_id = 主任务，则主任务完成后即可被拉取；若无依赖，创建后即可被拉取。  
  - **结论**：与现有依赖、拉取、调度兼容；需新增字段与「handler 内允许 create_task 并写入链字段」的约定。

- **资源清理**  
  - 单任务内分块：主任务结束即删临时文件，与现有「任务结束即释放」一致。  
  - 任务链表：链尾任务结束删临时文件，责任清晰；主任务 result 或链上约定需提供 temp_pdf_path 等句柄。  
  - **结论**：两种形态下责任边界清晰，不依赖未定义的「定时扫描」作为唯一清理手段。

### 10.4 设计合理性评估

| 评估项 | 结论 | 说明 |
|--------|------|------|
| **是否贴合现有体系** | 是 | 一期不引入子任务与链，仅新增任务类型与 handler；后续链模型与 depends_on/pipeline_id 并列，不推翻现有语义 |
| **边界是否清晰** | 是 | PDF 与 web_fetch 分离；单任务内分块 vs 任务链两种形态分阶段实现；链上「主任务分解、链尾清理」职责明确 |
| **是否可落地** | 是 | 单任务内分块仅需实现 handler 与配置；链扩展需 DB 迁移（链字段）+ handler 内 create_task 的调用约定 + 前端展示分组 |
| **是否易扩展** | 是 | 任务链表模型不限于 PDF，其它「先分解再执行、最后收尾清理」的流水线可复用同一套链字段与约定 |
| **风险与成本** | 可控 | 一期不碰表与 Worker 契约，风险低；链扩展需一次表结构变更与约定文档，避免各处「临时用 depends_on 凑」导致语义混乱 |

**总体结论**：现有任务管理体系与「PDF 转 Wiki」及「子任务/任务链表」新需求之间的关系已梳理清楚；**一期采用单任务内分块、不引入子任务** 与现有体系完全一致，设计合理；**后续若上子任务，采用「任务链表」模型** 与现有依赖、管道、调度兼容，且职责与资源清理边界清晰，设计合理且可扩展。

## 11. 总结

- **方案 A**：PDF 与 web_fetch 完全分离，采用独立任务类型 `pdf_to_wiki` 与专用「下载 → 拆分 → 转文字 → 翻译 → 写入」流水线。
- **超大文件**：通过「先下载落盘 → 按页/块拆分 → 逐块转文字与翻译」控制内存与超时；硬性限制（文件大小、页数、单块长度）保证可预测与安全。
- **执行形态**：一期采用单任务内分块；若后续支持子任务，推荐用 **任务链表** 模型（§9.4）：子任务视为有父子/链路关系的任务链，主任务只分解并入队，链尾任务负责清理资源，每个任务记录 `parent_task_id` / `chain_id` / `chain_index` / `chain_total` / `is_chain_tail`，与现有依赖字段并存。
- **严谨性**：限制与配置、超限策略、失败与部分完成、结果结构、实现阶段均在本文档中明确，便于实现与评审。

### 实施状态（任务链 DB 扩充）

- **已完成**：任务表已扩充链字段（`parent_task_id`、`chain_id`、`chain_index`、`chain_total`、`is_chain_tail`），`create_task` 支持上述可选参数，`get_task` / `list_tasks` 返回链字段；迁移为启动时 ALTER TABLE 补列，兼容已有库；现有任务（网文抓取、mediawiki_write 等）及全部相关单测、API 测试已通过，无回归。
- **待后续**：handler 内调用 `create_task` 创建子任务的约定、链尾清理逻辑、前端按 chain_id 分组/折叠展示。
