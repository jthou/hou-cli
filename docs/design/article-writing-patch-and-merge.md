# 写文章：基于 Patch 与 Git 风格合并的精确修改 — 设计方案

## 一、问题与目标

### 1.1 当前方案的局限

- **锚点式局部插入**：依赖「锚点」字符串在文中的唯一匹配，无法表达任意多处的精确修改；对空格、换行敏感，易匹配失败或误匹配。
- **整篇替换**：助手输出整篇修改文、用户「接受修改」会整体覆盖，无法与用户本地已做的其它修改「合并」，也无法精确审计「改动了哪些行」。

### 1.2 目标

- **精确合并修改**：修改以「差分」形式表达和应用，只改动需要改动的部分，其余与当前版本一致。
- **LLM 输出 patch**：写文章场景下，要求模型输出**版本之间的 patch**（unified diff），而非（或除）整篇正文，便于精确应用与审计。
- **多版本合并**：当存在分支版本（如当前工作版 vs 某历史版 / 助手建议版）时，用 **Git 风格的 3-way merge** 生成合并结果，冲突以标准冲突标记呈现，由用户解决。

---

## 二、核心设计

### 2.1 概念

| 概念 | 说明 |
|------|------|
| **Patch (unified diff)** | 描述「从版本 A 到版本 B」的文本差异，格式遵循 unified diff（如 `diff -u` 输出）。LLM 或工具生成 patch，后端**应用** patch 到当前文章得到新版本。 |
| **3-way merge** | 给定 base（共同祖先）、ours（当前）、theirs（待合并版本），计算合并结果；冲突处插入 `<<<<<<<` / `=======` / `>>>>>>>`，由用户解决。 |
| **应用 patch** | 将 patch 作用于当前文章；若上下文匹配则应用成功，否则失败（可支持少量 fuzz）。 |

### 2.2 流程概览

**流程 A：用户请求修改 → LLM 输出 patch → 应用 patch**

1. 用户输入修改意图（如「在 01 节后插入这段证据」），当前文章已注入上下文。
2. **约束 LLM 输出**：通过 system 或 user prompt 要求助手**仅输出**「当前文章 → 修改后文章」的 **unified diff**，且用约定标记包裹（如 `\n```patch\n...\n```\n`），便于解析。
3. 前端或后端从助手回复中解析出 patch 文本；用户点击「**应用 patch**」。
4. 后端调用「应用 patch」接口：对当前文章应用该 patch，得到新正文；成功则写入新版本并返回，失败则返回错误（如「patch 无法应用，上下文不匹配」）。
5. 可选：若 LLM 同时输出「说明 + patch」，则只解析 patch 部分用于应用；说明部分仅作展示。

**流程 B：合并两个版本（Git 风格）**

1. 用户选择「合并版本」（如：当前工作版 vs 某历史版本，或 vs 助手刚生成的完整建议版）。
2. 后端确定 **base**（如：两版本的共同祖先——可选为更早的历史版本，或当前版本作为 base、另一版作为 theirs）。
3. 后端执行 **3-way merge**（可用 `git merge-file` 或等价库），得到合并结果；若有冲突，结果中包含冲突标记。
4. 前端展示合并结果；若有冲突，提供「解决冲突」编辑（保留 ours / 保留 theirs / 手动编辑），用户确认后写回为新版本。

## 三、LLM 输出 Patch 的约定

### 3.1 格式要求

- **内容**：unified diff，即「从当前文章（old）到修改后文章（new）」的 diff。建议以「全文」为单文件 diff，便于应用。
- **包裹标记**：便于从流式/多段回复中截取 patch，例如：
  - 开始：`\n```patch\n` 或 `\n---BEGIN PATCH---\n`
  - 结束：`\n```\n` 或 `\n---END PATCH---\n`
- **规范**：diff 中路径可固定为 `article.md` 或省略；行号、上下文行（context）需与当前文章一致，否则应用时可能失败。

### 3.2 Prompt 约束示例（写入写文章技能 / 系统提示）

- 「当用户请求对文章进行修改时，你必须**仅**输出一个 unified diff（patch），表示从【当前文章】到【修改后文章】的差异。不要输出修改后的全文。将 diff 放在 \`\`\`patch 与 \`\`\` 之间。」
- 可补充：「diff 的上下文行（未改动的行）必须与当前文章完全一致，以便系统自动应用。」

### 3.3 失败与降级

- 若 **应用 patch 失败**（如上下文不匹配、行号错位）：可返回错误，并可选提供「将助手回复中的整段正文视为新版本并整篇替换」的降级入口（与现有「接受修改」一致），由用户选择。

## 四、后端接口设计

### 4.1 应用 Patch（已实现）

- **接口**：`POST /api/chat/article/apply-patch`
- **请求体**：`{ "session_id": "xxx", "patch": "unified diff 字符串" }`
- **行为**：
  - 取该会话当前文章作为「待打补丁」内容；
  - 使用统一 diff 应用逻辑（见下）得到新内容；
  - 若成功：`set_current_article(session_id, new_content, source="user")`，并返回新文章；
  - 若失败：返回 4xx 及原因（如 "patch 无法应用：上下文不匹配"）。
- **实现**：`backend/core/article_patch.py` 中自研「unified diff 解析 + 按行应用」逻辑，无外部依赖。

### 4.2 3-way 合并（已实现）

- **接口**：`POST /api/chat/article/merge`
- **请求体**：`{ "session_id": "xxx", "base": "base 全文", "ours": "当前版本全文", "theirs": "待合并版本全文" }`
- **响应**：`{ "status": "success", "content": "合并后全文（可能含冲突标记）", "has_conflicts": true/false }`
- **实现**：将 base/ours/theirs 写入临时文件，调用 `git merge-file -p` 输出合并结果；需系统已安装 git。

### 4.3 冲突解决后写回

- 用户在前端编辑「合并结果」（解决完冲突后）并提交，可复用现有 `PUT /api/chat/article`（整篇替换），将解决后的内容设为当前文章并记入版本。

## 五、前端交互

### 5.1 应用 Patch

- 当检测到助手回复中包含「patch 块」（如 \`\`\`patch ... \`\`\`）时，在该条消息下展示「**应用此 patch**」按钮。
- 点击后：将解析出的 patch 与 `session_id` 发给 `POST /api/chat/article/apply-patch`；成功则刷新文章预览与历史版本；失败则 toaster 提示错误，并可提供「仍用回复中的全文替换」的降级操作。

### 5.2 合并版本

- 在历史版本或文章预览区域提供「**合并版本**」入口：选择两个版本（或「当前」+ 某历史版本），请求 `POST /api/chat/article/merge`，展示合并结果。
- 若 `has_conflicts` 为 true：在编辑区展示带冲突标记的正文，高亮 `<<<<<<<` / `=======` / `>>>>>>>`，提供「保留上文 / 保留下文 / 手动编辑」快捷操作，用户确认后调用 `PUT /api/chat/article` 写回。

---

## 六、与现有能力的关系

- **保留**：整篇替换（「接受修改」）、历史版本列表与恢复、局部插入（锚点）可作为补充或降级路径保留。
- **新增**：以「LLM 输出 patch + 应用 patch」为主路径，实现精确合并；以「3-way merge + 冲突解决」支持多版本合并。
- **版本历史**：应用 patch 或合并后写回的内容，与现有一致，仍作为新 revision 写入 `article_revisions`，便于追溯。

---

## 七、实施顺序建议

1. **后端**：实现 unified diff 的解析与应用（库或自研），暴露 `POST /api/chat/article/apply-patch`。
2. **写文章技能 / Prompt**：约束 LLM 在「修改文章」时输出 \`\`\`patch ... \`\`\` 包裹的 unified diff；可选同时输出简短说明。
3. **前端**：从助手回复中解析 patch 块，展示「应用此 patch」按钮并调用 apply-patch；处理成功/失败与降级。
4. **后端**：实现 3-way merge 接口（临时文件 + `git merge-file` 或库）。
5. **前端**：提供「合并版本」入口与冲突解决编辑，写回后刷新预览与历史。

完成以上后，即可用「LLM 输出 patch + 应用 patch」做精确合并，并用 Git 风格 merge 处理多版本合并与冲突。
