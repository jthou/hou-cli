# 文件快速搜索功能设计文档

## 1. 功能概述

实现一个高性能的文件快速搜索功能，支持：
- 文件名模糊搜索（支持通配符、正则表达式）
- 文件内容全文搜索（平台支持情况不同）
- 多条件组合搜索（文件名、类型、路径、大小、修改时间等）
- 搜索结果排序和分页

## 2. 核心需求

### 2.1 搜索能力
- **文件名搜索**：支持通配符（`*.py`）和正则表达式
- **文件内容搜索**：macOS 原生支持，Windows/Linux 需额外实现
- **文件类型过滤**：按扩展名过滤
- **路径范围限制**：指定搜索根目录
- **元数据过滤**：文件大小、修改时间等

### 2.2 性能要求
- 小范围搜索（< 1000 文件）：响应时间 < 100ms
- 大范围搜索（> 1000 文件）：响应时间 < 500ms
- 支持结果排序和分页，避免一次性返回过多结果

## 3. 架构设计思路

### 3.1 整体架构

采用分层架构，通过平台适配器模式实现跨平台支持：

```
API 路由层
    ↓
统一搜索服务层（FileSearchService）
    ↓
平台适配器层（PlatformAdapter）
    ├── Windows 搜索实现
    ├── macOS 搜索实现
    └── Linux 搜索实现
```

### 3.2 核心组件职责

- **FileSearchService**：统一搜索服务接口，负责查询构建、结果格式化、排序分页
- **PlatformAdapter**：平台特定搜索实现，封装各平台的搜索逻辑
- **QueryBuilder**：查询构建器，将用户查询转换为平台特定的搜索命令
- **FallbackSearch**：降级搜索实现，当系统命令不可用时使用文件系统遍历

## 4. 跨平台搜索策略

### 4.1 Windows 平台

**策略**：优先使用文件系统遍历，后续可集成 Windows Search API

- **MVP 阶段**：使用 `pathlib.Path.rglob()` 递归遍历文件系统
  - 支持通配符和正则表达式匹配
  - 性能一般，但无需额外依赖
  - 适用于小到中等规模的目录

- **优化阶段**：集成 Windows Search API
  - 利用系统索引，性能更好
  - 支持文件内容搜索
  - 需要 Windows Search 服务运行

### 4.2 macOS 平台

**策略**：使用系统内置的 `mdfind` 命令

- 利用 Spotlight 索引，性能优秀
- 系统内置，无需安装额外工具
- 支持文件名搜索和内容搜索
- 支持路径限制和复杂查询

**实现思路**：
- 文件名搜索：`mdfind -name "pattern" -onlyin /path`
- 内容搜索：`mdfind "kMDItemTextContent == 'keyword'"`
- 解析命令输出，转换为统一的结果格式

### 4.3 Linux 平台

**策略**：优先使用 `locate/plocate` 命令，降级到文件系统遍历

- **优先方案**：使用 `locate` 或 `plocate` 命令
  - 利用系统索引数据库，性能好
  - 需要检查数据库是否存在
  - 数据库可能不是最新的，需要处理

- **降级方案**：文件系统遍历
  - 小目录直接遍历
  - 大目录使用异步遍历，限制深度

**实现思路**：
- 检查 `locate` 或 `plocate` 命令是否可用
- 检查索引数据库是否存在
- 不可用时自动降级到文件系统遍历

## 5. 错误处理和降级策略

### 5.1 系统要求检查（启动时验证）

**目标**：在启动时确保系统命令可用，避免运行时降级

#### macOS 平台
- **必需**：检查 `mdfind` 命令是否可用
- **验证**：执行测试查询验证 Spotlight 索引是否正常
- **失败处理**：如果不可用，提供明确的错误提示和修复指导
  - 提示用户检查 Spotlight 服务是否启用
  - 提供启用 Spotlight 的步骤说明

#### Linux 平台
- **必需**：检查 `locate` 或 `plocate` 命令是否可用
- **验证**：检查索引数据库是否存在（`/var/lib/mlocate/mlocate.db` 或 `/var/lib/plocate/plocate.db`）
- **失败处理**：如果不可用，提供明确的错误提示和修复指导
  - 提示用户安装 `mlocate` 或 `plocate` 包
  - 提示用户运行 `updatedb` 创建索引数据库
  - 提供安装和配置的详细步骤

#### Windows 平台
- **必需**：检查 Windows Search 服务是否运行（阶段三）
- **MVP 阶段**：使用文件系统遍历，但需要明确告知用户性能限制
- **失败处理**：如果 Windows Search 不可用，提供明确的错误提示
  - 提示用户启用 Windows Search 服务
  - 提供性能对比说明

### 5.2 运行时错误处理

- **异常捕获**：捕获命令执行异常，提供友好的错误信息
- **日志记录**：记录搜索过程和错误，便于调试
- **错误提示**：提供清晰的错误信息和解决建议，而不是自动降级
- **配置验证**：定期验证系统命令可用性，发现问题及时提示

### 5.3 降级策略（仅在用户明确配置时使用）

**原则**：尽量避免降级，优先确保系统命令可用

#### 降级场景（仅作为最后手段）
1. **用户明确配置**：用户主动选择使用文件系统遍历模式
2. **临时故障**：系统命令临时不可用，但提供明确的错误提示和恢复指导
3. **性能测试**：用于性能对比测试

#### 降级实现（如果必须使用）
- **文件系统遍历**：使用 `pathlib.Path.rglob()` 递归遍历
- **异步优化**：大目录使用异步遍历，限制搜索深度
- **性能警告**：明确告知用户降级模式的性能限制

### 5.4 错误处理最佳实践

- **启动时检查**：应用启动时验证所有必需的系统命令
- **明确错误提示**：提供清晰的错误信息和修复步骤，而不是静默降级
- **配置指导**：为每个平台提供详细的系统配置文档
- **监控和告警**：记录系统命令可用性状态，发现问题及时告警
- **用户选择**：允许用户明确选择搜索模式，而不是自动降级

## 6. 性能优化思路

### 6.1 搜索策略选择

- **小目录（< 1000 文件）**：
  - 直接遍历，实时搜索
  - 使用异步 I/O 提高并发性能

- **大目录（> 1000 文件）**：
  - 优先使用系统索引（mdfind/locate）
  - 限制搜索深度，避免遍历过深
  - 结果分页返回，避免一次性加载过多

### 6.2 后续优化方向

- **结果缓存**：缓存常用目录的文件列表，TTL 缓存定期更新
- **索引系统**：可选的自建索引系统（SQLite），用于 Windows/Linux 的内容搜索
- **并发搜索**：支持多个搜索任务并发执行

## 7. 模块组织思路

### 7.1 目录结构

```
backend/services/search/
├── file_search_service.py    # 统一搜索服务
├── query_builder.py          # 查询构建器
├── models.py                 # 数据模型
└── platform/
    ├── base.py               # 平台适配器基类
    ├── windows_search.py     # Windows 实现
    ├── macos_search.py       # macOS 实现
    └── linux_search.py       # Linux 实现
```

### 7.2 接口设计思路

- **统一接口**：所有平台实现统一的搜索接口
- **请求模型**：包含查询、路径、过滤条件、排序等参数
- **响应模型**：统一的搜索结果格式，包含路径、大小、修改时间等
- **API 路由**：在 `backend/api/routes.py` 中添加 `/api/search/files` 接口
