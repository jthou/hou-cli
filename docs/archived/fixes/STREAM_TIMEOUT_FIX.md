# 流式通信超时设计修复

## 问题描述

从终端输出看到：
- 后端正在正常工作，已经执行了4轮，每轮都有工具调用和结果
- 但在第5轮时，前端报错："流式请求超时: 任务处理时间过长（超过 5 分钟）"
- 但实际上后端还在继续工作（从日志可以看到第3轮视频下载成功，第4轮执行了execute_code）

## 根本原因

### 当前设计的问题

1. **前端超时设置**：
   - `stream_receiver.py` line 74: `timeout=timeout` (默认300秒，5分钟)
   - 这是 `httpx.AsyncClient.stream()` 的超时参数
   - **问题**：`httpx` 的 `timeout` 参数是**总超时时间**（total timeout），不是**空闲超时时间**（idle timeout）

2. **后端心跳机制**：
   - `routes.py` line 198-214: 每30秒发送一次心跳
   - 心跳通过 `__STATUS__` 消息发送
   - **问题**：即使后端每30秒发送心跳，如果总时间超过5分钟，前端仍然会超时

3. **设计矛盾**：
   - 后端有心跳机制（每30秒），但前端的超时是总时间限制
   - 对于长任务（如视频下载+处理），5分钟可能不够
   - 应该使用**空闲超时**（idle timeout）而不是**总超时**（total timeout）

## 解决方案

### 方案1：使用空闲超时检测（推荐）

在前端实现**空闲超时检测**：
- 如果超过一定时间（如60秒）没有收到任何数据，才认为超时
- 收到任何数据（包括心跳）都会重置计时器
- 这样即使任务总时间很长，只要后端持续发送数据（心跳或内容），就不会超时

### 方案2：增加总超时时间

将 `httpx.AsyncClient.stream()` 的 `timeout` 设置为 `None`（无限制）或一个很大的值（如3600秒，1小时）

### 方案3：使用 httpx 的详细超时配置

使用 `httpx.Timeout` 对象，分别设置：
- `connect`: 连接超时（如10秒）
- `read`: 读取超时（如60秒，空闲超时）
- `write`: 写入超时（如10秒）
- `pool`: 连接池超时（如10秒）

## 推荐实现

结合方案1和方案3：
1. 使用 `httpx.Timeout` 配置详细超时
2. 设置 `read` 超时为60秒（空闲超时）
3. 在前端实现额外的空闲超时检测（双重保障）
