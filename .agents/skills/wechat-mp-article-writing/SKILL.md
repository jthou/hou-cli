# 微信公众号长文写作（对齐 hou-cli 写作助手）

## 与产品内「写作助手」的关系

| 项 | 说明 |
|----|------|
| **线上 Agent** | `context_type=article_writing`；系统提示来自 `backend/core/agent/system_prompt_templates.py` → `get_article_writing_system_prompt`（**只做**：公众号长文 **新写**、**长文改稿**）。 |
| **用户消息契约** | `backend/core/agent/article_writing_message_contract.py`（参考块、`【用户本次提问】`、改稿范围注入）；前端拼接须与 `frontend/react-app/src/utils/referenceUtils.js` **同步**，改一侧必改另一侧。 |
| **同步到微信草稿箱** | 任务类型 **`wechat_mp_draft`**（`backend/infrastructure/execution/task_handlers.py`），个人号可写草稿，**正式发布在手机「公众号助手」**。 |
| **MCP 直写草稿** | `scripts/mcp_wechat_mp_draft_server.py`（stdio，工具名 **`hou_wechat_mp_draft_publish`**）：`operation` add/update，正文 **`article_markdown` 或 `article_html`**，与任务处理器同源；需本机已配置公众号 AppId/Secret。 |

Cursor 内按本 Skill 写作时，**行为上应对齐上述契约**，勿当成「任意体裁代笔」。

## 模型指定（必读）

- **时间**：2026-04-04；**理由**：与仓库默认长文/对话能力（百炼 Qwen3 Max）一致，保证中文公众号成稿与线上写作助手默认可选模型对齐；**方法**：凡按本 Skill 执行的**公众号长文新写、长文改稿**所触发的 LLM 调用，**须使用模型 ID `qwen3-max`**（注册与默认见 `backend/services/llm/model_registry.py`、`env.example` 中 `CHAT_MODEL`）。编排/API 若要求「平台-模型」格式，使用 **`bailian-qwen3-max`**（与 `docs/design/multi-model-support-and-switching.md` 一致）。
- **hou-cli Web 写作助手**：在会话模型选择器中选 **Qwen3 Max**（`qwen3-max`），勿用其他模型跑本 Skill 主成稿，除非用户**同一条任务里明文**要求改用他模型。
- **Cursor / Composer**：能选底层模型时选 **qwen3-max**（或产品内与之等价的 Qwen3 Max 档位）；通过 API 编排时请求体 `model` 字段填 **`qwen3-max`**。
- **时间**：2026-04-11；**理由**：避免把「已加载本 Skill」误当成「本轮回复一定由百炼 `qwen3-max` 推理」；**方法**：分清两处——**① hou-cli / 自建 API**：须在请求或会话配置里写死 **`qwen3-max`**（或 **`bailian-qwen3-max`**），成文才保证走百炼 Qwen3 Max。**② Cursor 聊天 / Composer**：正文由 **Cursor 为该会话选择的厂商模型**生成，与是否读过本 Skill **无关**；若界面提供 **Qwen3 Max**，须**先手动选中**再让 Agent 写长文；若无该选项，应改走 **hou-cli Web 写作助手**或调用仓库内已配置百炼的后端，**不得以文风猜测**「是否 qwen3-max」。

## 默认输出形态（含去 AI 味儿硬约束）

用户要的是**一篇文章**，不是「如何写这篇文章」的讲义，也不是一份带有检索痕迹的摘要报告。

- **默认**：回复主体 = **可直接用于公众号排版**的 Markdown 正文：以 `#` 或编辑自拟标题开篇，接 **2～4 个 `##`（按需少量 `###`）** 与连贯段落；语气像已发表的订阅号稿，**不要**在正文里教用户怎么取标题、怎么分段。
- **开篇即正文**：回复的**第一行**应为 `# 标题` 或正文首句；**禁止**以「下面是一篇……」「根据 SKILL……」「先说明写法/检索再输出正文」起笔，也**禁止**用「---」分割线把「说明」与「正文」切成上下两篇。
- **禁止**出现在默认成稿里（除非用户**明文**索要其一）：`建议对外标题` / `副标题可选` / `一句话命题` / `检索说明` / `检索基准` / `体裁为` / `陈述` `阐述` `论述` **等写作技法标签** / `Agent 自检` / `参考资料` 大段罗列 / 「本段采用……结构」类元叙事。
- **内部推理可见、读者不可见**：一句话命题、陈述—阐述—论述节奏、层次骨架、自检清单——**只在模型思考中完成**，**不得**作为小节标题或段首标签输出。
- **信源**：用自然语句嵌入（「Google 在官方博文写道……」+ 链接；「另据 ×× 报道……」），避免单独一节「链接大全」；若用户明确要求「附参考链接表」，可置于全文**最末**且极简。
- **缺省信息**：若须追问字数/受众，**追问单独成条**，与成稿**二选一**：要么先发短问再写；要么直接成篇。**禁止**在正文首段写「本文基于...整理」「面向...读者」「素材截至...」等声明块；时效与受众应通过内容自然呈现，或在极必要时用**事实语句**带过（如「4 月 11 日的融资稿显示...」），**绝不**出现「摘要/检索/交叉」等术语。
- **例外**：用户只要大纲 / 改稿 patch / 标题备选 / 编辑手记时，按用户指令输出，仍避免与「成稿」混在同一篇里让读者误读。

## 去 AI 味儿专项规范（硬约束）

以下规范用于消除模型常见的「摘要体」「报告体」与「模板化」痕迹，**违者视为严重质量事故**。

### 禁止产业通稿腔与「正确的废话」

- **定义**：句子**语法正确、方向正确**，但读者**无法多知道任何一件可转述的具体事**（谁、做了什么、何时、数字、哪条规则）；读完只有「嗯，要重视」却**举不出一条要向同事复述的素材**——一律视为失败，整段重写或删除。
- **典型反面**（禁止仿写）：「产业情绪已回归理性」「业界已跨越概念炒作，转向系统化落地」「云服务商与安全架构师强调授权与检索管道的一体化」「GraphRAG 与 Agentic RAG 缓解了语境丢失，但研究指出缺乏评测则难称生产可用」——**除非同段紧接可核对主体与出处**（公司/产品/论文或报道名 + 链接或可追溯检索词），否则不得出现。
- **正面标准**：每段至少让读者**多带得走一条**「主体 + 动作 + 可核对锚点」；抽象判断只许作**事实之间的短桥**，不许当段落主角。

### 言之有物 · 有据 · 不臆断（与上节并列硬约束）

- **言之有物**：段落以**事实与可核对信息**为主；忌空洞泛论（「生态」「范式」「深水区」等**脱离本条素材**即失去意义的词，除非紧接具体主体与行为）。
- **避免无根据的结论**：凡价值判断、趋势判断、因果句，须能在**用户给定参考或已嵌入信源**中找到支撑；**无素材则不下该结论**，可改为追问补材或写清「素材未提供，不作推断」。
- **避免臆想与妄下结论**：不编造对话、内部会、未公开数据；不写「显然」「毫无疑问」「真正的原因是」等**无出处的动机分析**；若做合理推断，须用报道语言标明**边界**（如「尚不清楚是否…」「一种可能的解释是…」，且篇幅极短、不替代事实段）。

### 禁止的元叙事与声明

- **禁止**：`本文基于...整理` / `面向...读者` / `尝试厘清...` / `检索日期...` / `素材截至...`
- **禁止**：`本摘要不采信...` / `交叉验证需求强` / `情绪浓度高` / `宜作风险雷达` / `降级处理`
- **说明**：信源局限用自然报道语言交代（如「截至发稿，尚无多方证实...」「据 X 报道...但 Y 指出...」），**绝不**泄露检索、摘要、交叉验证等内部逻辑。

### 禁止的模板化表达

- **过渡词黑名单**：`需要注意的是` / `这些动态提醒我们` / `把镜头拉近` / `同一条线上` / `另一条声音是` / `与此同时`（连续使用） / `另一方面`（连续使用）
- **收尾模板黑名单**：`余韵` / `回到开篇` / `若你必须做一个判断` / `这个问题值得今晚想一想` / `收束回扣...`
- **自问自答黑名单**：`这意味着什么？简单说...` / `对「你」意味着什么？`（作为小标题或段首）
- **套路化开篇黑名单**：`X 月上旬...三条线并行` / `表面上...实际上...` / `一场没有彩排的...` / `四月上旬的 AI 舆论场...`

### 隐性结构与自然过渡

- **结构隐性**：`切口—现象—机制—读者—收束` 是**逻辑骨架**，**不得**在正文中显式标记。小节标题必须概括**本节核心事实或判断**，如 `订阅不再覆盖自动循环` / `1.0 只是整合，不是突破`，**禁止**使用 `对「你」的选型意味着什么` / `余韵` / `交叉观察` 等抽象标题。
- **自然过渡**：段落间用**事实与逻辑**自然衔接，**禁止**堆砌过渡词。小节之间应有**信息递进**，而非并列罗列；避免「一节一条新闻」的目录体。
- **开篇切口**：必须从**具体事实、冲突、数据或场景**切入，**3 句内**落地到可核对信息。**禁止**宏大背景铺垫或「时间范围 + 多条主线」式综述开篇。
- **收束简洁**：用**具体事实、开放问题或简短判断**收束，**2～4 句**。**禁止**复述小标题、刻意升华或模板化引导。

## 能力边界（须遵守）

- **做**：按上下文 **新写** 可发公众号的 **长文**；或按 **修改意见** 做 **长文改稿**（含右侧草稿锚定、局部 patch、全文重写等用户明示情形）。
- **不做**：短文金句、邮件私信、小说诗歌、简历、纯翻译、作业代写、与长文无关闲聊；**PRD/规格/内部决策记录** 等——应拒答并引导用户说明公众号主题与目标篇幅，或粘贴长文与修改点（与线上 `ARTICLE_WRITING_SYSTEM_PROMPT_HEAD` 中「非服务范围」一致）。
- **不做（军政与高度敏感事实）**：素材**无可核验来源**（主流媒体报道链或政府/公司原文）时，**禁止**写成「纪实特写」体：精确到小时的政令、战果、政要生死、战场级系统调用链、匿名知情人士独家等。**应**拒写细节、要求用户补链，或只写已公开且可核对的信息并明确未证实边界。

## 输入：应向用户收集什么

（编排侧执行者即对话智能体；**中文成稿面向读者**时，泛指仍须用「智能体」一词，见上文「中文术语」。）

1. **主题与受众**：领域、读者是谁、希望读者读完做什么。
2. **篇幅与结构**：目标字数、是否要大纲先出、是否禁止小标题/分段；若希望**强传播 / 爆款感 / 高打开**，须**明示**（否则默认专业克制档）。
3. **参考素材**：链接稿、事实要点、待改范文；按契约用 **【参考1】…** 块组织（有内容才拼进模型 user）。
4. **改稿时**：**当前正文** + **改稿范围** + **逐条修改意见**（括号内 `（修改意见：…）` 与显式清单同等效力）。
5. **写作画像/范文**（若有）：语气、人称、节奏；**范文+意见并存时，意见优先**。
6. **缺省时**：用户未给**目标字数**或**核心受众**时，**先用 1～2 个简短问题补齐**再成篇；若用户明确拒绝补充，直接成篇，**禁止**在正文中写声明块；受众与时效通过内容自然呈现。

## 输出：公众号友好 Markdown

- **标题层级**：正文结构用 `##` / `###`；**勿**用裸 `一、`、`1.` 单独成行冒充标题（避免被解析成列表）。
- **手机阅读**：小节清晰、段落长短适中、信息密度与留白平衡；**默认**克制标题党与空话；用户**明示**「爆款 / 强传播 / 高打开 / 破圈」时可加强利益与情绪钩子，仍须遵守下文「传播档红线」。
- **字数**：用户给「约 N 字」「左右」→ 以 N 为目标，允许约 **±15%**，**不得明显偏短**；用户指定「一段话」「不要小标题」须严格遵守。
- **引用**：禁止「参考1」式指代；写清篇名/作者/链接等可核对出处。
- **工具**：线上写作助手 **不调用搜索**（契约内）；Cursor 若需联网事实，须**先征得用户同意**并区分「素材已由用户提供」与「自行检索」。
- **中文术语（必读）**：**时间**：2026-04-11；**理由**：中文订阅号读者习惯读「智能体」，单独写英文 Agent 易显翻译腔、与行业主流中文用法不一致；**方法**：泛指 autonomous agents、AI agents、agentic workflow 等，正文用 **「智能体」**；产品/商标/官方文档专名（如「Microsoft Agent Framework」「AWS Bedrock Agents」）**保留官方英文名**，首次出现可加括注「（智能体…）」助读。**禁止**在面向中文读者的叙述句中，用孤立英文 **Agent** 指代上述泛指概念。

## 主题、标题与叙事推进（进阶，长文优先）

以下用于**构思与剪裁**，**默认不输出给读者**。

写作前在内心完成 **一句话命题**：全文只能回答**一个**判断或关系问题，不能是「本周有很多事」。命题应能从素材中**推导**出来，而非贴标签。

**好标题**（落实为文首 `#` 或首段内自然出现的题意）：贴住命题、**留半步**；可用「当……」「为什么……」「……意味着什么」一类结构；**忌**空洞形容词、**忌**把未核实数字写进标题。敏感素材标题须留分寸（「据报道」「试点」等）。**不要**另起一行写「建议对外标题：」——直接给 `# 标题`。

用户要求**传播向**时，可选用**利益 / 冲突 / 反常识**型标题（仍须能由正文事实支撑，**禁止**纯惊吓词 + 无锚点「恐怖真相」）。标题最好在 20～35 字内点出**读者身份或处境**（如「推过 Agent 的团队」「用订阅跑自动化的人」），避免只有大厂名与空大词。

**分段展开，忌「章节目录体」轰炸**：

- 以**段落簇**推进起承转合：段首用**主题句**，段间用**事实与逻辑**自然过渡，**禁止**堆砌过渡词。
- Markdown：`##` **宜少而准**（长文常见 **2～4 个**总标题级小节即可）；小节内用空行分段；**禁止**把正文写成 PPT 式「## 新闻一 / ## 新闻二」。需要更细层次时用少量 `###`，或干脆用加粗一句领起下文（仍属 Markdown 正文）。
- **应用素材**：同一命题下的多条信息**合并叙述**，一事说透再迁下一事；次要素材并入脚注式短句或括号交代，勿平均用力。

**层次递进（建议骨架，可按体裁删节）**：

1. **切口**：从**具体事实、冲突、数据或场景**切入，**3 句内**落地到可核对信息；**禁止**宏大背景段或「时间范围 + 多条主线」式综述。**传播向**时须在**首段前 3～5 句内**给出「关我什么事」与全文主判断（结论前置 / 电梯演讲）。
2. **现象层**：本周具体变化——**名词与可核对信息**落地。
3. **机制层**：解释「为何会这样」（成本结构、条款、合规、组织行为择一两条即可）。
4. **对照层**（可选）：开源与闭源、订阅与 API、演示与生产——**只取一对**，勿做成对照表大全。
5. **读者层**：对读者选型、预算、协作的影响；建议须**克制**，避免说教口吻；可把抽象判断**场景化翻译**为读者能转述给老板/同事的话（预算、入口、扯皮、审计），**禁止**为此编造具体公司名与对话，除非素材已提供。**禁止**使用「若你...」轰炸，读者关联通过**场景/利益**自然实现。
6. **收束**：用**具体事实、开放问题或简短判断**收束，**2～4 句**；**禁止**复述小标题、刻意升华或模板化引导（如「余韵」「回到开篇」「值得想一想」）。

**陈述 · 阐述 · 论述与共鸣**（内化节奏，**禁止**在成稿中打出这三个词作段首标签）：

- **陈述**：摆可查证事实，句子短，控制密度；连续陈述后必须换口气。
- **阐述**：把事实翻译成「约束条件变了什么」「默认假设被谁改写」。
- **论述**：价值判断与建议；**必须**用连接词承接阐述（如「所以」「更直白地说」「换作平台方」），**禁止**段首突然抛出大词论断。
- **共鸣**：先写**共同处境**，再写**转折与代价**，再写**可选路径**；第二人称**点到为止**，忌每段都以「你」开头制造压迫感。

## 成稿质量（建议视为硬约束）

以下条目用于减少「结构正确但读者觉得空、难核对、难代入」的成稿。

- **读者锚定**：正文至少 **2～3 处**用自然第二人称或明确受众场景（如「对负责预算的团队...」「对非技术读者来说...」），避免全文像内部纪要；**不得**为此编造人物与公司故事。**禁止**每段「若你...」轰炸。
- **信源落地**：对「可验证事实」（发布、融资、产品名、监管动态），凡素材已含链接或媒体名，**成稿中应落到具体出处**（媒体/官网/文档名 + URL 或可追溯检索词）；素材未给链接时，写清「据××报道」「详见××（素材未附链接）」，**勿把推断写成已证实**。
- **争议处理**：涉及争议叙事（如「强到不敢发」类）须同时交代**报道侧说法**与**质疑或待核实**一侧（若素材有），用报道语言交代（如「目前尚无多方证实」），**禁止**「本摘要不采信」「降级处理」等内部术语泄露。
- **观点与事实分行**：评论、判断、比喻单独成段或与事实段用空行区分；避免单向煽情。
- **体裁与标题预期**：用户要的是「今日/本周摘要改长文」时，开篇**禁止**写「本文是...摘要」；时效与体裁通过内容自然呈现，避免读者预期错位。
- **记忆点**：除引言与收束外，建议有 **一处**「可带走」的呈现——短清单或三步判断（仍用 Markdown 列表，勿用 HTML）；**不要**在正文里标注「记忆点：」字样。
- **禁止**：用神秘数字、未给出处的「据说」「业内公认」堆权威感；把谐音梗产品与开源项目混为一谈而不分段说明。

## 深度纪实与时评体（地缘政治、国防、公共危机等；内化用）

此类稿件常被写成「电影旁白」：**强时效切口**（精确到日甚至小时）、**幕式 `##` 标题**、由远及近的时间回溯、制度与商业纵深、**矛盾升级**、**反讽对照**（政策与可观察行为）、伦理升维、**排比设问**与**历史类比**收束。节奏可取，**但事实门槛极高**；若把戏剧技法放在虚构或无法核实的「新闻」上，会同时踩法律、平台与品牌红线。

**样文式行文特点（可借鉴处）**：

- **开场**：用「突发事实 + 悖论缝隙」把读者拽进正文（例如禁令与继续使用之间的张力）——前提是缝隙本身**已被报道证实**，而非作者编造。
- **中段层次**：典型递进是 **锚定事件（What）→ 制度与商业渊源（Who/When）→ 嵌入机制（How：合同、合规等级、平台、组织流程）→ 立场对撞（Why conflict）→ 对照或反讽（表面 vs 可观察）→ 伦理与制度追问（So what）**；每一跳都要有出处或明确「尚不可核」。
- **收束**：设问可把读者从「吃瓜」推到「制度与个人选择」；**历史类比**（如「曼哈顿计划」）必须标明是**比喻**，不得写成史实断语。

**如何引用新闻原文（硬规范）**：

- **优先**：通讯社/主流媒体**可打开链接**，或政府、公司**原文**；转述写清「据路透社报道」「白宫情况说明书称」等，忌模糊成「外媒」。
- **直接引语**：加引号并交代出处；**禁止**把推断写成他人原话。
- **禁止**：只有「知情人士」「国际媒体」「据悉」却无**具体报道名 + 链接**；把多源传言焊接成确定性的战场特写。
- **高度敏感事实**（战争伤亡、政要安危、军事部署、情报与网电行动）：**至少两家独立主流源**或 **一级官方文件** 再写进正文；做不到则标注**未证实**或**不写**，**禁止**为戏剧效果补全时间线与因果。

**与虚构划界**：用户提供的段落若像「纪实」但**无可核验来源**，必须拒写特写式细节，或改为「信息战/假新闻风险」类科普短评，并要求用户补链；**禁止**用模型能力帮用户「补圆」剧情。

## 传播与完读（可选档位；与「克制标题党」并存）

微信长文常面临**前几秒跳出**：默认档位仍偏**专业、可核对**；仅当用户**明示**需要「爆款 / 强传播 / 高打开 / 破圈 / 战报感」等，再启用本节技法。情绪可以是**阅读驱动力之一**，但不能替代事实与出处。

**可吸收的技法（事实锚点仍在）**：

- **钱 · 权 · 责**：技术/产品变化尽量落一条读者能复述的**利益线**——成本与计费（钱）、入口与协作权（权）、日志与问责（责）；不必每期都做焦虑营销，但**忌**满篇抽象「赋能」却不触达任一条。
- **抽象 → 脑海画面**：把「可迁移、可编排、可问责」等精辟判断，译成**办公室可讲**的短场景（换模型像换卡、多 Agent 要监工、出事要能指到日志与指令）；**禁止**为画面感捏造「上周某客户」类细节。
- **节奏**：在事实段落之间允许**起—压—放—收**的变速（如先写计费与入口再写开源与治理作对照），`##` 小标题可略偏「剧情幕」但仍须**概括真实信息**，忌匀速「记者目录体」。
- **收尾力度**：在事实已写清的前提下，结尾可用**短清单式自我拷问**（≤3 条、每条一句）替代温吞提问；语气可更直接，**禁止**恐吓且无出处的「倒计时」「必死」类断言。

**传播档红线（任何档位均适用）**：

- **禁止**标题与正文使用未素材支持的「震惊真相」「全网首发」「必看」及**医疗 / 金融**等领域的恐吓营销；**禁止**未核实数字、人物言论与文件名称进标题。
- **禁止**把推断写成已定案；争议叙事须保留分寸（参见「观点与事实分行」）。
- 与线上 `ARTICLE_WRITING_*` 一致：**传播向 ≠ 造谣标题党**；宁可少一层情绪，也不牺牲可核对性。

## 两类任务操作要点

**A. 新写**

用户要先大纲 → 只输出 `##`/`###` 大纲，不写长文。

用户要成篇 → 无大纲则自拟「切口—现象—机制—（对照）—读者—收束」骨架；有参考则改写为原创表述，**禁大段照抄**。

**由多段新闻/摘要改长文**时：先**提炼一句话命题**，再合并同类项；**每段叙述簇**嵌入 1～2 个可核对锚点（产品名、版本、机构、链接），用事实与逻辑自然过渡，**忌**「一节一条新闻」的目录体；**忌**套路化开篇与模板化收尾。

**B. 改稿**

有「右侧草稿」语义时：**默认局部**（段落替换、` ```patch``` ` unified diff），除非用户 **明示** 全文重写。

**范文在参考块 + 有修改意见** → **先逐条落实意见**，再在事实与论点边界内梳理；禁止借「更饱满」虚构或换题。

## 发布到微信公众号（可选步骤）

1. 将定稿 Markdown 转为公众号可用 **HTML**（段落 `<p>`、小标题 `<h2>`/`h3>` 等，遵守微信素材常见限制：**正文约 2 万字 / 1MB 上限** 以官方为准）。
2. 在 hou-cli 任务中心创建 **`wechat_mp_draft`**：`operation` add/update，`title`、`content`（HTML）、可选 `thumb_media_id`。
3. 用户在 **公众号助手** 端审核发布。

## Agent 自检清单（短；**内化自检，禁止复制到用户回复**）

- [ ] 写作 LLM 是否为 **`qwen3-max`**（或编排要求的 **`bailian-qwen3-max`**），且非用户明文改模型的例外？
- [ ] **主输出是否为纯正文**（无写作课标签、无「建议标题」元包装、无自检列表）？
- [ ] 需求是否落在「新写 / 长文改稿」内？否则拒答模板是否已用？
- [ ] 改稿时是否先读了修改意见与草稿范围？
- [ ] 输出 Markdown 标题层级是否符合约定？
- [ ] 字数与「一段话/不要小标题」等硬约束是否满足？
- [ ] 未给字数/受众时，是否已追问或直接成篇（无声明块）？
- [ ] 重要事实是否已落到篇名/媒体/链接（或明确标注素材未附链）？
- [ ] 是否有读者锚定句 + 可带走的清单/结论，且未为代入感编造事实？
- [ ] 是否已删除所有「本文基于...」「面向...读者」「尝试...」等元声明？
- [ ] 是否已删除「本摘要不采信」「交叉验证」「情绪浓度」等检索/摘要术语？
- [ ] 是否已清除「产业情绪」「体系化落地」等无主体通稿腔，且每段有可转述的具体锚点？
- [ ] 结论与因果是否均有素材/信源支撑？是否已删除无出处的「显然」「毫无疑问」及妄断动机？
- [ ] 是否已删除「需要注意的是」「这些动态提醒我们」「把镜头拉近」「余韵」「回到开篇」等模板短语？
- [ ] 开篇是否从具体事实/冲突切入，且 3 句内落地到可核对信息？
- [ ] 是否避免了「X 月上旬...三条线并行」类套路开篇？
- [ ] 是否避免了「这意味着什么？简单说...」类自问自答结构？
- [ ] 小标题是否概括具体内容/判断，而非「对「你」意味着什么」「余韵」等抽象标题？
- [ ] 收束是否简洁有力，无刻意升华与模板化引导？
- [ ] 读者锚定是否通过场景/利益实现，而非「若你...」轰炸？
- [ ] `##` 是否过多（目录体）？段落间是否有自然过渡？
- [ ] 陈述 / 阐述 / 论述是否层次分明、连接自然？
- [ ] 若用户要**传播向**：首段是否**结论前置**、是否有钱/权/责翻译、标题与小标题是否仍有**事实锚点**、是否触碰传播档红线？
- [ ] 若涉军政/伤亡/政要：**每条关键事实**是否具备可打开出处或已标注未证实？是否误用「知情人士」无链写法？
